---
title: ADR-027 — Cross-template scope graph for the LSP
---

## Context

[ADR-026](/adr/adr-0026-editor-capability-matrix/) fixed the LSP capability
matrix and listed four capabilities the server deliberately does NOT ship —
`textDocument/definition`, `textDocument/references`, `textDocument/rename`,
`textDocument/documentHighlight` — on the grounds that the engine has no
cross-template scope graph: partials and helpers are looked up at runtime
through a host-supplied registry the engine never indexes. Without an editor-
side index, those four capabilities would either return nothing or fall back
to text-shaped string search (strictly worse than the editor's built-in word
highlight).

This record proposes the missing scope graph as a *separate, future work
item* outside the editor surface — an engine-level addition that, once
shipped, would unlock the four LSP capabilities almost mechanically.

## Decision

A cross-template scope graph is a workspace-scoped index built and maintained
by the language server, structured around the two named references FlatBars
templates actually carry:

* **Partial names** — every `{{> name}}` (and `{{#> name}}`) is a reference;
  every `{{#*inline "name"}} … {{/inline}}` block (ClassicBars) is a definition.
* **Helper / operation names** — every identifier the painter resolves
  through `editors/operations.json` is a reference to the catalogue entry;
  user-defined helpers registered via `registerHelper` (ADR-018) are
  definitions only the host knows about (out of editor scope until the
  registry abstraction lands).

The index is workspace-rooted: the LSP scans every file whose URI extension
maps to a dialect (`dialectForUri` returns non-null), parses each into the
token stream, and records `(name, defLocation)` and `(name, refLocation)`
tuples. Two collections per workspace:

* `partialDefinitions: Map<name, Location[]>` — the locations of inline
  declarations.
* `partialReferences: Map<name, Location[]>` — the locations of `{{> name}}`
  invocations.

Capability wiring:

* `textDocument/definition` on a partial-name token (in either an inline
  declaration or an invocation) returns the matching definitions.
* `textDocument/references` returns all matching invocations (plus the
  definition when `includeDeclaration` is set).
* `textDocument/rename` proposes a `WorkspaceEdit` rewriting both the
  definition and every invocation.
* `textDocument/documentHighlight` (the in-file slice) returns the
  definitions and references that share the file with the cursor.

The index is *eventually consistent*: built on `workspace/didChangeWatchedFiles`,
re-indexed per-file on `textDocument/didChange`, garbage-collected on
`textDocument/didClose` when the URI leaves the workspace. The LSP serves
stale answers between batches rather than blocking on a full re-scan — the
worst stale answer is "no result" which the four capabilities tolerate.

## Phased plan

1. **Phase 1 — read-only scanner.** Add `editors/lsp/src/index.mjs` that
   consumes the engine's `tokenize` over every workspace file and builds the
   two maps. No LSP wiring yet; expose `definitionsOf(name)` /
   `referencesOf(name)` for tests.
1. **Phase 2 — `textDocument/definition` + `documentHighlight`.** Wire the
   first two capabilities into `server.mjs`; advertise both in the
   `InitializeResult`. The single-buffer documentHighlight degrades to the
   word-bounded set of references in the active file when the index is cold.
1. **Phase 3 — `textDocument/references`.** Same shape as definition; honours
   `includeDeclaration`.
1. **Phase 4 — `textDocument/rename`.** Returns a `WorkspaceEdit` with one
   `TextEdit` per occurrence. A pre-check rejects renames whose target collides
   with an existing partial name.
1. **Phase 5 — helper / operation references.** Treat catalogue identifiers as
   references too; the catalogue entries themselves are the definitions
   (synthetic locations into `operations.json`).

Tests at each phase: per-fixture corpus under `editors/lsp/test/fixtures/`
asserting the index's contents, the capability's response, and at least one
multi-file scenario.

## Consequences

* Unblocks the four ADR-026 omissions without requiring a language-level
  module system. The engine itself stays unchanged — the LSP owns the index.
* Adds workspace scanning to server startup; on large workspaces (10K+
  templates) the initial scan needs streaming and progress notifications.
  Implement with `workspace/configuration` so users can cap the scope.
* `registerHelper`-style host-defined helpers remain unreachable until the
  registry abstraction in ADR-018 grows an editor-visible projection.
* User-defined inline partials in non-ClassicBars dialects are unreachable as
  written — RawBars/MaxBars do not have `{{#*inline}}`. Either the partial
  registry is host-provided (unindexable today) or partials become a
  filesystem convention (one `.classicbars` file per partial name).

## Status

Proposed 2026-06-04. Implementation is gated on a small `tokenize`-based
scanner; no language-level changes are required.
