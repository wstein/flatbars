*Status:* Accepted. *Date:* 2026-06-01. Companion to [ADR-001](/adr/adr-0001-structural-parser-and-walker/)
(one structural parser) — this record extends the same "one grammar, derived downstream" principle to
syntax highlighting. Implementation plan: `highlighting-spec.md`.

## Context

FlatBars renders template syntax in (at least) two front-ends — the FlatBars Lab editor (CodeMirror 6,
a hand-written `StreamLanguage`) and the tutorials site (a regex overlay behind the runnable-example
card). Each grew its own tokenizer. Together with the engine's own lexer that makes *three* definitions
of FlatBars surface syntax:

. the authoritative one — `FlatBars.Lexer` + `FlatBars.Token` (`tokenizeInterior`), the meaning-free
  structural tokenizer ADR-001 rests on, dialect-scoped through `LexOptions` / the `parseExpr` seam;
. the Lab's template highlighter — a CodeMirror `ViewPlugin` over a hand-written tag regex
  (`HB_TAG_RE` + `hbMarkFor`); *not* the engine, and a separate regex from (3);
. the tutorials' regex highlighter (`tutorials/src/lib/highlight.mjs`).

(2) and (3) are *separate* regex approximations of (1) — they drift from the engine and from each
other (e.g. the Lab's `hbMarkFor` mis-classifies `{{<p}}`/`{{$b}}` inheritance as plain
expressions; neither handles set delimiters or MaxBars operators). A fourth and fifth definition exist
for the host *data* format: the tutorials hand-roll a line-regex YAML highlighter, while the Lab uses a
real `lang-yaml` grammar plus a bespoke value decorator (see `highlighting-spec.md` §1 for the full
audit). Two template bugs shipped from this:

* *Exhibit A* — `Hello, {{!-- name --}}!` highlighted the comment as closing at the inner
  `}}`, leaving `--}}!` as plain text. The regex did not know the `{{!-- … --}}`
  long-comment form, which the engine's `RComment` / `openerLiteralAt` handles.
* *Exhibit B* — the regex painted an unterminated `{{!--` as a closed comment plus a separate
  raw tag, while the engine swallowed everything to the next `--}}`. *The highlighter and the
  engine disagreed about where a tag begins and ends* — i.e. the highlighter lied about what the engine
  would parse.

This is precisely the class of drift ADR-001 and the project's "one source of truth, derived
downstream" gates (`check:catalog`, `test:compile`, `examples:verify`) exist to prevent. Highlighting
had no such gate, so the drift was silent.

## Decision

. *Highlighting is a structural concern and MUST derive from the engine lexer.* Tokenizing template
  source for display is the same job the meaning-free lexer already does. Front-ends MUST NOT fork the
  grammar. The engine exposes a tokenization API (`highlightSpans(template, dialect)` →
  positioned whole-tag spans; a thin `FlatBars.Highlight` core module over the lexer; see
  `highlighting-spec.md`), shipped in the same `flatbars-js` bundle the Lab and
  tutorials already load. A single `kind → CSS-class` map is shared; presenters differ (a CodeMirror
  `ViewPlugin` for the Lab, a highlight-layer overlay for the tutorials) but the *grammar is one*.

. *Per-dialect by construction.* Because the source is the dialect-scoped lexer (`LexConfig`,
  `LexOptions`, `parseExpr`), each dialect's tag boundaries and roles are coloured correctly without
  per-dialect highlighter code: set delimiters (the stateful `mustacheDelims` pair) on RawBars/MaxBars/
  MinBars, the inheritance sigils `{{<}}`/`{{$}}`, and — critically — the clause
  separators `{{else}}` / `{{elif …}}`, which paint as *statements* only when the head is
  one the dialect treats as a separator. That set is the parser's own `standaloneSeps`
  (`["else","elif"]` for the kernel dialects, *empty* for MinBars, where `else` is just a variable) —
  IoC, the same seam `trimStandalone` consults, never a hardcoded keyword list. A regex cannot even
  *tokenize* MaxBars (operator chars vs path chars) nor know a dialect's separator set, which is
  decisive against the regex as a permanent solution. *A tag is coloured as one span by its meaning* —
  the structural role of its head (interpolation, block, partial, comment, …). Interior tokens
  (operators, string and number literals) are *not* singled out: a literal carries no meaning of its
  own beyond "an argument to this tag", so painting it a second colour competes with the tag's role
  rather than clarifying it. (An earlier iteration tiled each tag with `operator` / `string` / `number`
  sub-spans; it was removed in favour of this one-colour-per-meaning rule. The per-token `end` offset
  that enabled it stays in `FlatBars.Token.PosToken`, and now *is* the substrate for the editor token
  vocabulary's interior axis — `tokenize` ([ADR-017](/adr/adr-0017-editor-support-lsp/), implemented)
  carves those interior spans for the LSP/TextMate layer, while `highlightSpans` stays one-colour-per-tag.)

. *A drift gate is mandatory* (`check:highlight`, mirroring `check:catalog`), wired into `npm test`.
  Highlighting joins "measured, not asserted": a lexer change not reflected in highlighting fails the
  build.

. *Implemented (the stopgap is retired for template syntax).* The engine API landed as
  `highlightSpans` (`FlatBars.Highlight`, on the `flatbars-js` facade). Both front-ends now paint
  template syntax from it — the Lab via the shared `lab/cm-flatbars.mjs` CodeMirror plugin, the
  tutorials via `highlightTemplate(src, dialect)` rewritten over `highlightSpans`. The template regexes
  (the Lab's `HB_TAG_RE`/`hbMarkFor`, the tutorials' `TAG_RE`/`highlightTemplate` body) are *gone*.
  `check:highlight` is now engine-derived (golden = `highlightSpans`), so a lexer change unreflected in
  highlighting fails the build. An interior-token pass was tried and *reverted*: a tag is coloured as one
  span by its head's meaning (§2), so operators/strings/numbers inside a tag get *no* span of their own.
  The enabling substrate stays — `FlatBars.Token.PosToken` carries an `end` offset — and is now consumed
  by the opt-in LSP/TextMate vocabulary's `tokenize` ([ADR-017](/adr/adr-0017-editor-support-lsp/),
  implemented), not by `highlightSpans`. One follow-up
  remains, an *enhancement, not the bug class this ADR closes*: full CodeMirror 6 adoption in the
  tutorials (real `lang-yaml`, a single presenter with the Lab), deferred for bundle weight. Host-*data*
  (YAML) highlighting — the Lab's `yamlDecorator`, the tutorials' `highlightYaml` — is a separate concern
  and is unchanged. See `highlighting-spec.md`.

## Amendment (2026-06-04): the highlighter shares the parser's tokenizer

This ADR's principle — highlighting derives from the engine lexer — is now
literal: `tokenizeSpans` no longer re-runs `tokenizeInterior` itself. It scans
via `tokenizeTemplate` (which now lexes each tag's interior at scan time) and
carves interior spans from the tag's *pre-lexed* interior — the same `RawTok`
stream the parser consumes
([ADR-004](/adr/adr-0004-token-lexer-and-grammar-seams/) amendment). The
highlighter and the parser therefore read every interior off the *same* token and
cannot drift on how it is lexed. Byte-identical: the `check:highlight` golden was
unchanged by the migration.

## Consequences

* The Lab's and the tutorials' template regexes are retired: both now paint from the shared
  `highlightSpans`. The `check:highlight` corpus was the acceptance set that the engine-driven
  highlighter kept green, so the migration was verifiable rather than a leap.
* `flatbars-js` gained a public, stable tokenization surface (`highlightSpans`) — also useful for future
  editor features (semantic colouring of known vs unknown helpers via the schema/catalog, error
  squiggles from the lexer's `ParseError` spans).
* The golden gate (`scripts/gen-highlight.mjs`) is now an *engine-equivalence* oracle: its golden is
  `highlightSpans(src, dialect)` from the committed bundle, covering the set-delimiter, per-dialect, and
  clause-keyword cases a regex cannot. Long `{{!-- … --}}` comments are coloured as one span: the
  lexer emits them as a span-only `RLongComment` under `keepLongComments` (a flag only the highlighter
  sets, so the render/compile token stream is unchanged), bounded exactly as the engine parses them —
  which is what the regex got wrong in Exhibits A/B.
