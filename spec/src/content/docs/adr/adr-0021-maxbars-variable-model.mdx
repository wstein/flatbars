*Status:* Proposed. *Date:* 2026-06-03. *Supersedes* [ADR-006](/adr/adr-0006-maxbars-loop-variables/)
Decision §1–2 (the bare loop-variable vocabulary) and §5 (its v1 outer-loop limit). *Extends*
[ADR-013](/adr/adr-0013-labelled-loops/) (labelled loops → `outer`). Applies to *MaxBars and RawBars*
only; FullBars is unchanged (Handlebars-faithful).

*Amendment (2026-06-07).* The flat enclosing-loop names `parent-index` / `parent-key` /
`parent-first` / `parent-last` are **removed**. The enclosing loop is reached through the
`loop` chain instead — `loop.parent.index0`, `loop.parent.key`, … (deeper nesting climbs
`loop.parent.parent.…`) — and `loop` is now a first-class scoped root in the catalog. FullBars'
`@../index` lowers to `(lookup loop "parent" "index0")` (byte-identical; the Handlebars `@data`
namespace and the bare `index`/`index0` aliases are otherwise unchanged — `index` could **not** be
removed because `@index` is the `@data` key host block helpers supply). The on-demand lint migrates
`parent-index` → `loop.parent.index0` (etc.).

*Amendment (2026-06-08).* MaxBars drops the Handlebars block-param bars, and a bar
in a block head is now a parse error — whether it was the `as |a b|` delimiter or an
unparenthesised pipe (so the old "stray head bar" warning is retired; a pipe must
still be parenthesised, `{{#each x in (xs | f)}}`). The two loop-binding surfaces:

* **`{{#each}}` binds Liquid-style** — the names come *before* `in`, the collection
  after: `{{#each item in items}}`, `{{#each item i0 i1 in items}}`. Up to three
  names bind (element, 0-based index/key, 1-based index — one more than FullBars'
  two). `{{#each items}}` (no `in`) is the binding-less form.
* **`{{#with}}` keeps a drop-pipes `as`** — `{{#with x as p}}` (and custom block
  helpers take their block params the same way).

FullBars keeps the Handlebars bars (`as |a b|`) unchanged — the spelling is selected
by the same reserved-variable capability that selects the variable model. A
companion surface refinement: the `..` range operator (`1..n` ⇒ `(range 1 n)`), free
in MaxBars because `../` parent-paths are already gone (above), plus the `[…]`/`{…}`
collection literals and block-scoped `{{#let}}` ([ADR-024](/adr/adr-0024-let-and-dict-literal/)/[ADR-025](/adr/adr-0025-list-literal/)).

*(An interim build within this cycle used a trailing `as a b` on `each` too; it was
superseded by the `… in coll` spelling before release.)*

## Context

Three things converged to make the loop/context vocabulary worth redesigning:

* *ADR-006 bare loop variables* gave MaxBars `{{index0}}`, `{{first}}`, `{{length}}`,
  `{{key}}`, … as *bare* scoped names. They silently shadow data fields — the schema-less
  *warn-always* lint (`loopVarShadowWarnings`) exists *only* to paper over that footgun — and they reach
  just the *current* loop.
* *ADR-013 labelled loops* added `label NAME` → the loop frame reified as an object
  (`{{outer.index1}}`). It proved the mechanism: *a dotted head resolves against a binding only
  when the name is scope-declared* (`{{c.deep.n}}` works because `c` is a block param;
  `{{root.title}}` / `{{parent.title}}` render *empty* because `root`/`parent` are frame
  helpers but **not** scope-declared, so they parse as data paths).
* *Reaching the enclosing / root context* still relied on Handlebars' `@root` and `../` — the
  `@` namespace the non-Handlebars dialects want to drop.

The decision: replace the bare magic vocabulary with a small set of **reserved, namespaced, chainable**
scoped names, and drop `@`/`../` in MaxBars and RawBars.

## Decision

1. *The model is `this` / `loop` / `root` / `parent` / `outer`* — five reserved scoped names, available in
   *MaxBars and RawBars*. FullBars is untouched: it keeps `@index`/`@root`/`../` (Handlebars
   fidelity) and does *not* get these names. The set is *complete*: current context (`this`), current-loop
   metadata (`loop`), a named enclosing loop's metadata (`outer`/labels), enclosing context (`parent`),
   root context (`root`).

1. *Frames chain.* Every frame-shifting block (`each`, `with`) pushes a frame linked to its parent frame
   and the root. The reserved names resolve against this chain, and **chain from day one**:
| Name | Resolves to |
| --- | --- |
| `this` | the current context (raw data). Unchanged. |
| `loop` | the *current loop's metadata object* (`each` only) — see the loop-object shape below. Chains over enclosing *loops*: `{{loop.parent.index0}}`, `{{loop.parent.parent.length}}`, `{{loop.root.length}}`. |
| `outer` | a *named* enclosing loop's metadata object (any `label NAME`, ADR-013) — same shape as `loop`. |
| `parent` | the *enclosing context* object. Chains over enclosing *contexts*: `{{parent.name}}`, `{{parent.parent.name}}`. |
| `root` | the *root context* object (outermost context). |
`loop`/`outer` are *loop metadata* (chain over enclosing **loops**); `parent`/`root` are *contexts*
(chain over enclosing **contexts**). They are complementary, not redundant: `{{loop.parent.index0}}`
is the enclosing loop's index; `{{parent.name}}` is a field on the enclosing context.

1. *Object shapes (normative).*
* *loop-object* (`loop`, `outer`, any label): `{ index0, index1, rindex0, rindex1, first, last, length,
  key, this, parent, root &#125;`. The index/`first`/`last`/`length` arithmetic is ADR-006's (`rindex0 =
  length − 1 − index0`, `first = index0 == 0`, …); `this` is the element; `parent` is the nearest
  *enclosing loop*'s loop-object (or `null`); `root` is the *outermost loop*'s loop-object (or itself).
  An **immutable per-iteration snapshot**.
* *context-object* (`parent`, `root`): the context's *own* fields, plus the reserved links
  `{ this, parent, root }` (reserved names win on collision). `parent` is the enclosing context-object
  (or `null` at the top level); `root` is the root context-object.

1. *Reserved-name resolution (the mechanism).* The reserved names are **scope-declared** so a dotted head
   resolves the binding, not a data path — the ADR-013 mechanism, generalized.
* *MaxBars* — the surface desugar **seeds** the reserved names into `scope` (so `{{loop.first}}`
  desugars to `(lookup (loop) "first")`, not a data lookup). This seeding is *MaxBars-only*: it rides the
  same dialect hook that already distinguishes MaxBars from FullBars (which seeds nothing). This is "the
  MaxBars-only scoped-name seeding."
* *RawBars* — has no surface desugar, so the names are reached as ordinary *operations* the frame
  installs, in RawBars' explicit style: `{{{loop}}}`, `{{{lookup loop "first"}}}`,
  `{{{lookup (lookup loop "parent") "index0"}}}`.
* The *engine* installs the same frame bindings for both dialects; FullBars' surface routes bare names to
  data lookups, so it never reaches them — no gating of the bindings is required.

1. *`@` and `../` are removed in MaxBars* — at the parser seam (`parseMaxExpr`/`parseMaxHead`): an
   `@`-prefixed name or a `../` run is a *located parse error* that points the author at `root` /
   `parent` / `loop`. MaxBars-local; FullBars' default parser keeps both. RawBars never had `@`/`../`
   (no surface), so there is nothing to remove there.

1. *The bare loop-variable vocabulary differs by dialect* (amends ADR-006 §1–2; reconciled with the
   shipped frame, 2026-06-07). MaxBars uses `reservedScope noLoopVars`, so bare `{{first}}` / `{{index0}}` /
   `{{length}}` / `{{key}}` are ordinary *data fields* — the loop metadata is reached through `loop.*`
   (`{{loop.index0}}`); only the reserved roots `this`/`loop`/`root`/`parent`/`outer` resolve bare.
   **RawBars** (no surface) is the exception: the engine *does* install the bare scoped operations on the
   frame, so RawBars keeps its explicit `{{{index0}}}` / `{{{first}}}` / `{{{key}}}` (and `loop.*` works
   there too). What *was* fully removed in both dialects is the flat **`parent-*`** family — `parent-index`
   / `parent-key` / `parent-first` / `parent-last` → the `loop.parent.*` chain. (`index` and `index0`
   co-exist; the lint prefers `index0`.)

1. *The block-partial body is the reserved name `yield`.* Handlebars' `{{> @partial-block}}`
   yield is unwritable in the non-Handlebars dialects — `@` is reserved (§5), and a bare `partial-block`
   lexes as the subtraction `partial - block` under MaxBars' infix arithmetic. `yield` is added as a
   hyphen-free *synonym* of the `partial-block` scoped operation, installed under both names in the
   partial block frame, so the one yield is spelled `{{yield}}` (MaxBars), `{{{yield}}}`
   (RawBars), and `{{> @partial-block}}` (FullBars, unchanged). It is reserved like the other
   roots: a same-named data field is shadowed (read it with an explicit `{{lookup this "yield"}}`),
   and a `label yield` is flagged by the label-shadow lint. The yield is escape-safe (`VSafe`), so
   MaxBars' `{{ }}` form does not re-escape it.

1. *The warn-always shadow lint is retired.* The footgun was "any field-like bare name silently shadows a
   field"; with the metadata behind `loop.`, the reserved roots are `this`/`loop`/`root`/`parent`/`outer`
   (and `yield` inside a block partial) — explicit, and rarely data fields except `yield`, whose escape
   hatch is the explicit lookup above. ADR-006's `loopVarShadowWarnings` is deleted. The
   ADR-013 `labelShadowWarnings` (a `label NAME` colliding with a reserved root — `this`/`loop`/`root`/
   `parent`/`yield`) stays; a lighter optional lint may warn when a data field named one of the roots is
   shadowed in a block body. NOTE: a reserved root shadows a field *everywhere*, even through an explicit
   `{{this.NAME}}` (the path reduces to the segment `NAME`), so the explicit `lookup` is the only
   field escape.

1. *Compiler parity.* The frame chain + reserved-name objects are emitted by the compiler exactly as the
   interpreter builds them — the ADR-013 `rt.each`/`childFrame` `binds` chain extends to carry `loop` /
   `parent` / `root` and the parent links — gated by `test:compile` (interpreter ≡ compiled).

## Examples

```handlebars
{{!-- MaxBars --}}
{{#each row in rows label outer}}
  {{#each row.cells}}
    {{loop.index1}}/{{loop.length}}       {{!-- this (inner) loop --}}
    {{outer.index0}} of {{outer.length}}  {{!-- the named enclosing loop --}}
    {{loop.parent.first}}                 {{!-- the enclosing loop, unnamed --}}
    {{parent.heading}}                    {{!-- the enclosing context (a row) --}}
    {{parent.parent.title}}               {{!-- two contexts up --}}
    {{root.report.id}}                    {{!-- the root context --}}
  {{/each}}
{{/each}}
```

## Alternatives considered (team debate)

* *Flat names, no chaining* (`loop`/`outer`/`parent`/`root` but no `parent.parent`/`loop.parent`) —
  rejected: developers expect chaining from day one.
* *Hierarchy only* (`this`/`loop`/`outer`, fold `root`/`parent` under `loop`) — rejected: `root`/`parent`
  are not conceptually under `loop`, and the folding breaks in `{{#with}}` bodies (no `loop`).
* *Keep `@`/`../` alongside the new names* — rejected: the goal is to *drop* `@` in the
  non-Handlebars dialects; coexistence defeats it.
* *MaxBars-only (exclude RawBars)* — rejected by requirement: the model is for both non-Handlebars
  dialects. The asymmetry is only in *reach* (MaxBars: dotted paths via seeding; RawBars: explicit
  operations), not in the underlying bindings.
* *Keep the bare vocabulary for backward compatibility* — rejected: repo policy is no compat shims; the
  bare vars become data fields and templates migrate (below).

## Migration

* *MaxBars:* bare `{{index0}}`/`{{first}}`/… → `{{loop.index0}}`/`{{loop.first}}`;
  `{{@root.x}}` → `{{root.x}}`; `{{../x}}` → `{{parent.x}}`. Touches the
  `mx:loopvars-*` conformance cases, the `loopVars`/`loopObject` tutorial examples, the MaxBars
  interpreter `loopvars-*` tests, and `maxbars.adoc`.
* *RawBars / core corpus:* the bare `{{{index0}}}` / `{{{key}}}` / `first` / `last` are **kept** (RawBars'
  explicit scoped operations); only the removed `{{{parent-index}}}` → `{{{lookup loop "parent" "index0"}}}`
  (the `each-parent-index` case).
* *Lint:* delete `MaxBars.Lint.loopVarShadowWarnings` + its tests; keep `labelShadowWarnings`.
* *Docs:* this ADR; supersession note on ADR-006 §1–2 + its §5 v1 outer-loop limit; extended-by note on
  ADR-013; `nav.adoc` registration; `maxbars.adoc` and the RawBars page.
* *Build:* regenerate the Lab bundle; `test:compile` and full `npm test` green.

## Consequences

* *Pro:* one coherent, chainable, namespaced model; the shadow footgun is essentially gone (metadata is
  behind `loop.`); `@`/`../` are dropped from the non-Handlebars dialects as intended; reuses the
  ADR-013 frame mechanism.
* *Con:* a *breaking change* to every MaxBars/RawBars template using bare loop vars or `@`/`../`
  (no compat shim); a non-trivial migration; the reserved roots now shadow same-named fields inside a
  block body — `yield` most notably, a common data field (bond/crop yield), whose only escape is the
  explicit `{{lookup this "yield"}}`; building the frame *chain* (`parent`/`root` links,
  multi-level) is more engine/compiler work than ADR-013's single frame.

## Open questions

* `parent` at the *top level* (no enclosing context): propose `null`; `root` is always available.
* Whether to expose `loop.depth` (nesting depth) — *defer* to a follow-up.
