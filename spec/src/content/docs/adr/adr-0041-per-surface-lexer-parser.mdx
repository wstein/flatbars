*Status:* **Accepted** (MaxBars delivered — all four phases, see §8). *Date:* 2026-06-11. Applies to
the **front-end** (lexer + structural parser) of every *production* surface. **Starts with MaxBars**
(the PureScript reference / oracle for the Trussbars production engine); RawBars, ClassicBars, and
MinBars stay on the shared front-end for now and are extracted later (or deliberately kept shared —
see §6). Amends
[ADR-001](/adr/adr-0001-structural-parser-and-walker/) (the meaning-free shared parser) and the
dialect-ladder framing of [ADR-005](/adr/adr-0005-dialect-ladder/); builds on the *pure-grammar*
direction the Trussbars engine already took (first-class, non-superset surface — no lenient
Handlebars superset).

## 1. Context

ADR-001 established a single, meaning-free front-end — one lexer (`FlatBars.Lexer.tokenizeTemplate`)
and one structural parser (`FlatBars.Parser`) — that **every** dialect plugs into through options:

- **`LexConfig` / `LexOptions`** knobs: `statementTags`, `mustacheDelims`, `keepLongComments`,
  `operatorChars`, `rangeOperator`, `collectionLiterals`.
- **`ParseOptions`** seams + gates: `parseExpr`, `parseHead`, `extras`, `inheritance`, `decorators`,
  `partialBlocks`, `rawBlockHbs`/`rawBlockHash`, `standaloneSeps`.

`maxOptions = defaultParseOptions { … }` is exactly this: MaxBars is *a configuration of the shared
front-end*. That was the right call for a **construction kit** — it let four surfaces share one
recovering parser, one highlighter, one provenance map, and proved the IoC thesis.

It is the **wrong** call for a **production, frozen surface**. The shared, heavily-parameterized
front-end is a liability the moment a surface needs to be *stable*:

1. **Cross-surface coupling is a live bug class, not a hypothetical.** A separator is parsed by the
   *output* grammar and split into a `Sep` by its head — fine when `parseExpr == parseHead`
   (ClassicBars), but for MaxBars the two grammars differ, so `{{elif a < b}}` folded into
   `lt((elif a), b)` and the `elif` clause was silently lost. The fix had to thread MaxBars-aware
   logic (`clauseSeps`) through the **shared** parser — i.e. a MaxBars concern leaking into core, to
   be re-validated against *every* dialect on every change.
2. **The surface contract can't be frozen independently.** "Stable MaxBars 1.0" means *its* grammar
   stops changing — but it shares a parser that must keep changing for ClassicBars/MinBars/RawBars.
   Every shared-parser change is a potential MaxBars regression, gated only by conformance breadth.
3. **The lexer carries every other dialect's grammar in the hot path.** MaxBars rejects Handlebars
   `{{&}}`/`{{^}}`/bare-`{{{{…}}}}`, Mustache set-delimiters, and the inheritance sigils — yet its
   render still walks a tokenizer full of those branches (and the gate rejections that police them).
   A *pure* MaxBars grammar has none of that surface area.
4. **"Pure grammar" is already the Trussbars direction.** The Rust engine deliberately dropped the
   lenient Handlebars-superset lexer for a first-class grammar. The PureScript oracle should match, or
   it can't be the oracle for a pure-grammar production engine.

## 2. Decision

**Each production surface owns its structural front-end — its own lexer and structural parser — and
they share only the *semantic* layers below.** Starting with MaxBars:

- **Fork** the structural lexer and structural parser into `packages/maxbars` as `MaxBars.Lexer` and
  `MaxBars.Parser`.
- **Trim** them to the *pure MaxBars grammar*: delete every branch MaxBars rejects (§3), so there is
  no dead grammar and no gate-rejection machinery for shapes the surface never accepts.
- **Bake the config in.** No `LexConfig`/`LexOptions`/`ParseOptions` knobs at the MaxBars boundary —
  `MaxBars.parse :: String -> Either (NonEmptyArray ParseError) { directives, nodes }` is a frozen,
  argument-free entry. The `parseMaxExpr`/`parseMaxHead` interior grammar (already MaxBars-owned)
  moves under this front-end instead of being injected into the core.
- **Emit the shared `Syntax` AST.** The fork is front-end only; it produces the same `Content` /
  `Output` / `Block` / `Sep` / `RawBlock` nodes, so everything below is untouched.

### What stays shared (deliberately)

The **semantic** stack — it is dialect-agnostic and *not* what "stop sharing the lexer/parser" asks
to split:

- the `Syntax` AST (`Node`/`Template`), `Expr`, `Value`, `Span` — the contract the back-end reads;
- the **back-end**: `ClassicBars.Surface` desugar, `Kernel` engine / provenance / inspect / schema,
  the compiler, `Kernel.Walk`/`Lower`.

So MaxBars's pipeline becomes `MaxBars.parse → (shared) desugar → (shared) engine/compile`. Only the
`String → Template` front edge is unshared.

## 3. The trim list (what `MaxBars.Lexer`/`MaxBars.Parser` delete)

MaxBars's gates already reject these; the fork removes the *code paths*, not just the runtime guards:

| Dropped | Why MaxBars doesn't need it |
| --- | --- |
| `RAmp` (`{{& x}}`) | Handlebars unescaped-output extra (`extras = false`). |
| `Inverse` sigil (`{{^x}}`) | Handlebars inverse section (`extras = false`). |
| bare `{{{{name}}}}` raw block (`rawBlockHbs`) | MaxBars uses the `{{{{#name}}}}` spelling only. |
| inheritance sigils `{{<`, `{{$` (`Parent`/`BlockDef`) | MaxBars inheritance is `{% extends %}`/`{% block %}` (ADR-040), lowered, not a tag sigil. |
| `RSetDelim` / `mustacheDelims` (`{{=A B=}}`) | Mustache-only (MinBars); MaxBars rejects delimiter switching. |
| `decorators` (`{{#*inline}}`), `partialBlocks` (`{{#>}}`) | MaxBars uses bare `{{#inline}}`; partial-block is ClassicBars. |
| the `LexConfig`/`LexOptions`/`ParseOptions` knobs themselves | one frozen MaxBars config, inlined. |

What MaxBars **keeps** (now first-class, not knob-gated): `{% … %}` statement tags, `{# … #}`
comments, `{{ }}` / `{{{ }}}` output, `{{#name}}…{{/name}}` blocks, the `{{{{#name}}}}` raw region,
standalone-line trimming, the infix-operator / `..` range / `[…]`·`{k:v}` collection lexing, and the
recovering scan (ADR-023) — MaxBars keeps best-effort recovery + located errors.

## 4. Phases (each a green, independently-committable unit)

1. **`MaxBars.Lexer`** — fork `FlatBars.Lexer`, delete the §3 branches, inline the MaxBars
   `LexConfig`/`LexOptions`. Port the lexer's own unit tests (highlight/standalone/interior
   invariants) into `packages/maxbars`. Gate: byte-identical `RawTok` stream to the current
   `tokenizeTemplate maxLexConfig maxLexOptions` over a shared corpus (a transitional equivalence
   test, deleted in Phase 4).
2. **`MaxBars.Parser`** — fork `FlatBars.Parser`, delete the §3 gate machinery, inline MaxBars's
   structural choices, consume `MaxBars.Lexer`, plug `parseMaxExpr`/`parseMaxHead` directly. Expose
   `MaxBars.parse` / `parseRecovering`. Gate: byte-identical `Template` to `parseWith maxOptions`.
3. **Rewire** — point every MaxBars entry (`renderMax`, `compileMaxJs`, `inferMax`, mapped/inspect,
   the LSP/highlight path, the Lab `astJson` "maxbars" branch) at `MaxBars.parse`; drop `maxOptions`.
   Gate: the full conformance set stays green — `check:parity` (RawBars ≡ MaxBars), `examples`,
   `test:compile` (interpreter ≡ compiler), `check:provenance`, `check:parse-views`, the editor
   highlight/tmgrammar/vocab gates.
4. **Slim the shared core** — remove the now-MaxBars-only knobs from the shared front-end
   (`operatorChars`/`rangeOperator`/`collectionLiterals`, and any branch no remaining surface uses),
   and delete the Phase 1–2 equivalence tests. The shared lexer/parser shrink to exactly what
   RawBars/ClassicBars/MinBars need.

## 5. Consequences

- **Isolation (the point).** MaxBars's grammar can be frozen and versioned independently; a
  ClassicBars/MinBars parser change can no longer regress MaxBars, and MaxBars-aware logic
  (`clauseSeps`, the operator/collection lexing) leaves the shared core entirely.
- **Duplication is the accepted cost.** The structural scan + tree-build now exist in two places.
  Mitigation: the fork is *trimmed* (much smaller than the shared original), the AST + back-end stay
  single-source, and the Phase 1–2 equivalence gates pin the fork to the reference until it is
  intentionally allowed to diverge (the freeze).
- **The oracle role is preserved.** MaxBars still renders the canonical output the Trussbars engine
  conforms to; only *how it parses* is now its own, matching the Rust engine's pure grammar.
- **Highlighting / LSP follow the front-end.** `tokenize`/`highlightSpans` for MaxBars must run the
  MaxBars lexer (ADR-017's "highlight by running the engine lexer"); the editor vocabulary gates
  move with it.
- **Not a back-end split.** This explicitly does **not** fork the AST, engine, desugar, or compiler.
  Conflating them would be a far larger change with no production-stability payoff — the surface, not
  the semantics, is what needs to freeze.

## 6. Alternatives considered

| # | Alternative | Verdict |
| --- | --- | --- |
| **A1** | **Trimmed pure-grammar fork** (own lexer+parser, dead branches deleted, config inlined; shared AST + back-end) | **Chosen.** Maximal isolation + a lean, frozen, production grammar; matches the pure-grammar direction. |
| **A2** | Faithful fork (copy as-is, config fixed, keep every branch) | Rejected. Same duplication without the cleanup — carries dead grammar MaxBars never reaches, and a bigger surface to re-audit at the freeze. |
| **A3** | Owned thin facade (`MaxBars.Lexer`/`Parser` re-export shared internals with fixed config) | Rejected. A clean API but the implementation stays shared, so it does **not** stop sharing — a core-lexer change still reaches MaxBars (the exact coupling this ADR removes). |
| **A4** | Keep the shared front-end; freeze via conformance breadth only | Rejected (the status quo). Conformance catches regressions *after* they're written; it does not give MaxBars an independently-frozen grammar, and the coupling (§1.1) remains. |

## 7. Summary

- For a **production, stable** surface, the meaning-free *shared* front-end (ADR-001) becomes a
  coupling liability; each production surface should **own its lexer + structural parser**.
- **MaxBars first:** a *trimmed pure-grammar fork* into `packages/maxbars` (`MaxBars.Lexer` +
  `MaxBars.Parser`), config inlined, every rejected branch deleted, emitting the **shared `Syntax`
  AST** into the **shared back-end** (desugar/engine/compile unchanged).
- Delivered in four green phases (lexer → parser → rewire → slim the shared core), each pinned to the
  reference by an equivalence gate until the freeze.
- RawBars/ClassicBars/MinBars stay on the shared front-end for now; this ADR sets the pattern for
  their later extraction (or a deliberate decision to keep the compatibility dialects shared).

## 8. Outcome (as delivered)

All four phases landed green; `MaxBars.parse` is the production render/compile/inspect/infer/lint/
codegen path and `String → Template` never touches `FlatBars.Parser`. Two refinements to §3/§4 as
built:

- **Rejected shapes stay *recognized-then-rejected*, not lexically erased — a *learning-tool*
  behavior.** `MaxBars.Parser` rejects `{{&}}` / `{{^}}` / `{{<` / `{{$` / `{{#*}}` / `{{#>}}` / bare
  `{{{{name}}}}` with a located `DisallowedShape` whose message names the shape, rather than the lexer
  simply not producing those tokens. This is deliberate because of *what the PureScript engine is*: a
  multi-dialect **learning lab** that hosts ClassicBars (Handlebars) right next to MaxBars, so MaxBars
  keeps awareness of the Handlebars shapes precisely to *teach the contrast* — "that's a Handlebars
  form; the MaxBars way is …" — rather than emit a generic "unexpected `&`". The §3 *gate booleans* are
  gone (the rejection is unconditional grammar). `{{{ … }}}` raw output and `{{! … }}` comments **are**
  erased (`bracesOutputOnly` baked in — `{{{` is a lex error, `{{!` is `not` output, the comment is
  `{# … #}`).

  **This must NOT be ported to Rust Trussbars.** Trussbars is the *native standalone* engine — it has
  no Handlebars/Mustache concepts at all, so its grammar has only the six native sigils
  (`Output`/`Clause`/`Open`/`Close`/`Partial`/`Comment`) and a stray `{{&x}}` is simply a syntax error,
  like `@#$`, not "a rejected Handlebars shape". Teaching Trussbars about `{{&}}`/`{{^}}`/`{{<` just to
  produce a friendlier message would import compatibility knowledge the native reference deliberately
  lacks. The two implementations owe each other **conformance on valid input** (byte-identical render
  output over the corpus), not parity of rejection diagnostics: the lab contrasts dialects, the native
  engine stands alone.
- **MaxBars owns its *entire* front-end — four modules, not two.** Beyond `MaxBars.Lexer` +
  `MaxBars.Parser`, the fork extended to `MaxBars.Token` (the interior expression tokenizer, with the
  infix alphabet / `..` range / `[…]`·`{k:v}` collections baked in) and `MaxBars.Highlight` (spans from
  the owned lexer). Nothing in MaxBars's `String → Template`/spans path runs shared lexing code; it
  shares only the AST *types* (`Syntax`, `Token`/`PosToken`/`Interior`, `Value`, `Span`) and the
  back-end (desugar / engine / compile).
- **Phase 4 fully slimmed the shared core.** Removed from the shared front-end, all now-dead: the
  `ParseOptions.parseExpr`/`parseHead` seam + `ExprParser` type + `clauseSeps` gate (no remaining
  dialect distinguishes head from output grammar), and the `LexOptions` knobs
  (`operatorChars`/`rangeOperator`/`collectionLiterals`) + `defaultLexOptions` + `infixOperatorChars`
  (no remaining dialect sets them non-default). `FlatBars.Token`'s `tokenizeInterior` is now the fixed
  path/name-only grammar, and `FlatBars.Lexer.tokenizeTemplate` / `ParseOptions` / `HighlightConfig`
  shed their `lexOptions`. The shared front-end is exactly what RawBars/ClassicBars/MinBars need.
- The Phase 1–2 equivalence gates were retired with `maxOptions` once the fork became the production
  path; the full conformance suite (`test:compile`, `check:parity`, `examples`, `check:provenance`,
  `check:parse-views`, the highlight/vocab/tmgrammar gates, the differential handlebars/mustache
  proofs) now covers it.

### RawBars extracted too — the native/compat split

RawBars (the desugared-core `{% %}` surface) followed MaxBars: `RawBars.Lexer` / `RawBars.Parser` /
`RawBars.Highlight` own its front-end (it shares the path/name `FlatBars.Token` interior tokenizer —
it has no infix grammar — and keeps the Handlebars `{{{ }}}`/`{{! }}` output+comment forms it retains,
so `bracesOutputOnly` is off for it). `RawBars.purs` splits the owned dialect parse (`parseRaw`) from
the CLI's configurable core path (`parseCore opts`, the shared parser — preserving
`flatbars --compile --delimiters`). Every consumer (JS facade, CLI `lint`, `Linter.Lift`) was rewired
off `coreOptions`, which is now gone.

With MaxBars **and** RawBars off the shared lexer, nothing drove its `statementTags` / `bracesOutputOnly`
knobs, so the entire `{% %}`/`{# #}` statement-tag machinery (`readStatementTag`, `{% raw %}`,
`{% set/extends/include/yield/super %}`, `readInlineComment`, the `-` trim marker, …) was deleted from
the shared `FlatBars.Lexer`. **The shared front-end is now purely Handlebars/Mustache** (ClassicBars +
MinBars); the native `{% %}` family (RawBars/MaxBars/Trussbars) owns its lexers — the
native-vs-compatibility split the ecosystem positioning calls for. ClassicBars/MinBars conformance is
byte-identical (handlebars 49/50, mustache 184/184 unchanged). Only the two **compatibility** dialects
remain on the shared front-end; per §6 that is now a deliberate end state, not a pending extraction.
