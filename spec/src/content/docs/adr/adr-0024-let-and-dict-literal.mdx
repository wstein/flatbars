*Status:* **Accepted — both constructs implemented (2026-06-08).** The dict literal uses **JSON-style**
`{name: expr, …}` (a `:` separator, comma-separated pairs), *revising* the proposed `{name=expr name=expr}`
(`=`, whitespace-separated) of §2 below — see the *Amendment*. `{{#let}}` shipped as §1 specifies
(sequential, never re-rooting), as MaxBars-only sugar over the context-preserving `pushHelpers` frame push;
the *implementation note* on §1 records the one structural deviation (a kernel block operation rather than
a dedicated AST node); a ClassicBars `{{#let}}` is rejected with a located, actionable error (render +
LSP). Revised 2026-06-04 after team review (the list literal was split out to
[ADR-025](/adr/adr-0025-list-literal/)).
*Date:* 2026-06-04. Applies to *MaxBars and RawBars* only; *ClassicBars is unchanged*
(Handlebars-faithful — see [ADR-009](/adr/adr-0009-classicbars/) and the conformance line at
[ADR-005](/adr/adr-0005-dialect-ladder/)). Sits alongside
[ADR-021](/adr/adr-0021-maxbars-variable-model/) (the MaxBars/RawBars variable model) as the
expression-sugar half of the same dialect carve-out.

This ADR covers the two constructs that need *no shared-prelude change*: block-scoped `{{#let}}` and the
dict literal (which reuses the existing `dict` helper). The *list literal* needs a new `list` constructor
in the shared prelude, a different blast radius, so it is its own decision —
[ADR-025](/adr/adr-0025-list-literal/). The two ADRs share this Context and the lexing/dialect model.

*Amendment (2026-06-08, implementation).* The dict literal shipped as **`{name: expr, …}`** — a `:`
key/value separator, **comma**-separated pairs, keys a bare identifier or a quoted string — *not* the
proposed `{name=expr name=expr}` (§2). The reason is consistency with the [list
literal](/adr/adr-0025-list-literal/): a list **must** be comma-separated because MaxBars juxtaposition is
*application* (`[a b]` would parse as the single element `(a b)`), so the §"JSON-style literals" negative's
premise — that `:`/`,` could be avoided — does not hold once lists exist. With the list forced to commas,
a `=`/whitespace dict would split the two literals' surfaces gratuitously; one comma-separated family
(`[a, b]` / `{k: v, w: z}`) is the smaller surprise and the JS/JSON author's expectation. The ADR's *key*
decision is unchanged and upheld: distinct `{…}` (dict) vs `[…]` (list) shapes, so the empty-collection
case (`{}` vs `[]`) stays unambiguous. The `:` and `,` interior tokens are added behind
`LexOptions.collectionLiterals` (MaxBars-only). The §3 *width detection* is implemented: the structural
scanner is brace-aware under the same flag, so a dict abutting the tag close needs **no** space —
`{{#with {a: 1}}}` reads cleanly (initially shipped requiring a space; that caveat was removed
2026-06-08). The desugar target (the `dict` helper) and the dialect scope (MaxBars sugar; RawBars writes
`(dict …)`) are exactly as below.

## Context

Template authors recurringly need *template-local constants* — a forge-name → URL lookup table, a
status → label enum, an alias for a deep path used many times — that are intrinsic to the template,
identical on every render, and have no business in the host data. Today the only spelling is to pass
them in through the render context on every call, which is friction for what is effectively a `const`
inside the template.

Three things make this a design problem, not a one-helper fix:

* *No variables.* The [concepts](/concepts/) thesis is strict — *"the only compound expression is
  an application of a name."* Any new construct must either *be* an application or *desugar* to one. A
  literal expression class (`Lit`-typed nodes for `{…}`/`[…]`) cannot live in the kernel AST.
* *No host-format dependency in core.* [ADR-003](/adr/adr-0003-strict-layering/) keeps `JSON` ⇆ `Value`
  out of the core (*"JSON-ness is a host concern"*). YAML / JSON-style literal collections in *tag*
  bodies would re-import the same dependency under a different name.
* *Dialect carve-out is the established lever.* [ADR-005](/adr/adr-0005-dialect-ladder/) gives MaxBars
  the room for surface additions ClassicBars cannot have, by reuse-by-dependency: MaxBars depends on
  `classicbars`, swaps the interior expression grammar, and ClassicBars's Handlebars conformance
  (`49/50` byte-identical, gated by `check:hbs-conformance`) is untouched. [ADR-006](/adr/adr-0006-maxbars-loop-variables/)
  /[ADR-021](/adr/adr-0021-maxbars-variable-model/) use this for the variable model; this ADR uses it
  for `let` and the dict literal.

The space of candidates was enumerated in the design debate. The salient negative results — captured
here so future revivals don't relitigate, and shared with [ADR-025](/adr/adr-0025-list-literal/) —
were:

* *JSON-style literals* (`{"b":1,"c":2}`, `[1,2,3]`) — imported `:` and `,` as new tag-body tokens with
  no FlatBars precedent, broke whitespace-separated args, doubled the editor-tooling contract
  ([ADR-017](/adr/adr-0017-editor-support-lsp/) token-vocabulary).
* *Unified `[…]` for both dicts and lists*, content-disambiguated (all-`name=value` ⇒ dict, otherwise
  list). Killed by the empty-collection case: `[]` cannot mean both, leaving no literal spelling for
  the empty dict — and discarded the universal `{} / []` shape convention every comparable language
  (including Lua's tables) honours. This is *why* the dict literal is `{…}` (here) and the list literal
  is `[…]` (ADR-025), as two distinct shapes.
* *Dict sugar at the helper level only* (e.g. renaming `dict` → `obj`). One character saved per call,
  capped by name quality; not worth a prelude churn on a well-established helper.
* *Dropping `{{#with}}` in favour of `{{#let}}`*. `with` does two jobs (re-root context + optional alias);
  `let` does one (alias only). The aliases are equivalent only when the body never uses bare names. `with`
  also lives in the shared prelude, so removing it requires either splitting the prelude or adding a
  surface-level rejection — both heavier than the saving. See *Relationship to `{{#with}}`* below.

## Decision

Two constructs ship here, scoped to *MaxBars only*, *surface-stage* desugared, with *no shared-prelude
change*: block-scoped `{{#let}}` and the dict literal. (The list literal and its required `list` helper
are [ADR-025](/adr/adr-0025-list-literal/).)

### 1. Block-scoped `{{#let}}` — alias only, never re-root

> *Implementation note (2026-06-08).* Shipped as specified — sequential, never re-rooting — with two
> deviations from §5's sketch. (a) `let` is a **kernel block operation** (`Kernel.Prelude.letH`), *not* a
> dedicated `Let` AST node: it reads its bindings from the surface hash (MaxBars) **and** positional
> objects (the RawBars `(bind "name" value)` — `bind` is a one-key-object prelude helper, §4), then renders
> the body through the context-preserving `pushHelpers` (the env stack already had it). The sequential
> semantics come from **nesting** multi-binding lets into single-binding ones — `{{#let a=1 b=(add a 1)}}`
> ⇒ `{{#let a=1}}{{#let b=(add a 1)}}…` — so an inner binding's value is evaluated in the frame the outer
> installed (a single walk, no second pass). The compiled twin is `rt.letScope` (interpreter ≡ compiled,
> `test:compile`, including the RawBars `let-bind-*` cases). (b) The MaxBars-only scoping is enforced by **gating the desugar** to MaxBars, and a
> *ClassicBars* `{{#let}}` is **rejected** with a located `DisallowedShape` at render
> (`ClassicBars.checkSurfaceStrict`, alongside the bare-`{{#inline}}` rejection) whose message points to the
> `{{#with x as |n|}}` fix — not a silent no-op. The editor surfaces the same as an LSP diagnostic
> (`dialectDiagnostics`, gated by `check:dialect-diagnostics`). (The §Gates line below named
> `check:isolation`, which is dependency-scoped; the realized gates are the ClassicBars `let-rejected-*` unit
> tests and `check:dialect-diagnostics`.)

`{{#let}}` installs *nullary operations* at the block's lexical scope; they vanish at `{{/let}}`. It is
the operation model applied to template-local *constants* — no new concept, just a new way to write one.

```handlebars
{{#let n=expr [n=expr …]}}
  … body where each n is a nullary operation that returns expr …
{{/let}}
```

Semantics:

* *Bindings* evaluate left-to-right, each in the scope *extended by the bindings to its left*: in
  `{{#let a=1 b=(add a 1)}}`, `b` sees `a`. A binding sees neither itself nor any binding to its
  right, so there is no self-reference and no fixpoint — this is a *sequential* `let`, not a `letrec`,
  and it remains a single total walk (no second pass). The sequential form removes the nesting tax the
  earlier parallel design imposed (which forced `{{#let a=1}}{{#let b=(add a 1)}} … {{/let}}{{/let}}`
  for what is the common case).
* *Scope* is block-scoped lexically: names exist between `{{#let}}` and `{{/let}}`. Inner blocks inherit;
  partials called inside inherit (the standing scope-chain rule).
* *Shadowing.* A `let` name that collides with an in-scope helper shadows it inside the body, then the
  original is unshadowed at `{{/let}}`. A collision with a `{{#each xs as |x|}}` block param of the same
  name in the *same* scope is a parse error.
* *Does not re-root context.* `{{#let u=user}}{{name}}{{/let}}` resolves `name` against the *root*, not
  against `user`. To re-root, use `{{#with}}` (which stays — see below).

### 2. Dict literal `{name: expr, …}` — MaxBars expression sugar

> *Implemented form (see the Amendment above).* A brace-delimited list of `key: value` pairs in
> expression position is sugar for `(dict …)`. Keys are a bare identifier or a quoted string; values are
> full expressions; pairs are comma-separated. *(The original proposal was `{name=expr name=expr}` —
> `=`-separated, whitespace-separated; revised to the JSON-style form for consistency with the
> comma-separated list literal.)*

```handlebars
{{#let forges={codeberg: "…", github: "…", gitlab: "…"} }}
  …
{{/let}}
```

Desugars at the MaxBars parser stage to `(dict "codeberg" "…" "github" "…" "gitlab" "…")`. The `dict`
helper already lives in the shared prelude ([prelude](/engine/prelude/)); *no kernel or prelude change* — this is
the property that lets the dict literal ship ahead of the list literal.

Empty: `{}` is the empty dict — clean, unambiguous, lowers to `(dict)`.

### 3. Lexing: desugar at the MaxBars expression stage, structure lexer untouched

The dict literal is resolved entirely in the MaxBars interior grammar (`MaxBars.Expr`, plugged in
through the `ParseOptions.parseExpr` seam). The *structure* lexer (`tokenizeTemplate`) never gains `{` or
`}` as structural tokens, and tag-boundary detection is unchanged. This is what keeps the three
delimiter widths (`{{ }}` / `{{{ }}}` / `{{{{ }}}}`) intact: width detection runs *first* and fixes the
tag span; only then does the interior tokenizer see the literal braces. (ADR-025 extends the same
principle to `[`/`]`; the rule is identical.)

> *Implemented behavior (2026-06-08, revised).* The proposal below is implemented: the structural scanner
> (`tokenizeTemplate`) is **brace-aware** under `LexOptions.collectionLiterals` (MaxBars). When finding a tag's
> close it balances `{ }` depth and skips string literals, so a dict literal's own `}` — and any `}}`/`{`
> inside a dict-value string — is consumed before the tag close. `{{#with {a: 1}}}` and `{{{json {x: 1}}}}`
> read cleanly with **no** disambiguating space. (An interim build required a space; that caveat was removed
> the same day by making the scanner brace-aware — exactly the "width detection" §3 specifies.) The change is
> gated and inert for every other dialect, whose interiors never contain a `{`. Comments and set-delimiter
> tags are deliberately *not* brace-aware (a comment is prose; a stray `{` must not swallow its close).

The realized consequence for the surface: inside an already-delimited tag, the scanner matches `{`
against its closing `}` by nesting depth, so a literal collection's own closing brace is consumed before
the tag close. `{{#let x={a=1}}}` therefore reads as `#let x=` · `{a=1}` · `}}` (dict-close, then
tag-close), and the nested `{{#let x={a={b=1}}}}}` as `{a={b=1}}` · `}}` — no ambiguity, because
the tag span was settled by width detection before the interior is scanned. *Authors never insert a
disambiguating space.* This is the load-bearing lexing claim, so it is gated by a dedicated tokenizer
corpus (see *Gates*).

### 4. Dialect scope

| Surface | `{{#let}}` | `{…}` dict literal | Notes |
| --- | --- | --- | --- |
| *RawBars* | ✓ (explicit form: `{{#let (bind "a" x)}}…{{/let}}`) | ✗ (no sugar at all by design) | Writes the kernel form directly; `bind` is a prelude helper (a one-key object), nested for sequential scope. |
| *ClassicBars* | *✗* | *✗* | Handlebars-faithful. Authors use `{{#with x as \|n\|}}` for aliasing and `(dict …)` for collections. |
| *MaxBars* | ✓ (with `n=expr` surface sugar) | ✓ (`{name=expr …}`) | The flagship; the list literal is added by ADR-025. |

This is the same asymmetry already enforced for MaxBars operators (`>=` is MaxBars-only sugar that
lowers to `(gte …)`; `gte` is a shared-prelude helper).

### 5. Kernel footprint

One addition, small and decided here (not deferred):

* *A dedicated `Let [(name, expr)] body` AST node* (resolved during review — see below). It pushes a
  helpers-only frame onto the env stack at `{{#let}}` and pops it at `{{/let}}`. The env stack already
  exists — `pushFrame` (`Kernel.Env`) is what block params and `{{#with}}` use — but note `pushFrame`
  bundles *helpers + context*; `let` pushes the binding helpers while *passing the current context
  through unchanged* (that is the "never re-root" guarantee of §1, expressed mechanically). No new
  `Value` shape.

The dict literal adds *nothing* to the kernel: `{…}` desugars before the AST is built, so the kernel sees
an ordinary `Application` node — `(dict …)` — and `dict` is already in the prelude. (The list literal of
ADR-025 is the one construct that *does* touch the shared prelude.)

### 6. Relationship to `{{#with}}`

`{{#with}}` stays in *every* dialect. `let` and `with` are complements, not competitors:

| Operation | Alias | Re-root `this` / bare names |
| --- | --- | --- |
| `{{#let n=x}}` | ✓ | ✗ |
| `{{#with x}}` | ✗ | ✓ |
| `{{#with x as \|n\|}}` | ✓ | ✓ |

The identity worth recording: `{{#with x as |n|}}` ≡ `{{#with x}}{{#let n=x}} … {{/let}}{{/with}}`.
`let` desugars *part* of `with`, not the whole thing.

## Consequences

### Gates

* *Tokenizer corpus (precondition — must land before implementation).* A golden corpus in the
  `check:highlight` style that pins the lexing claim of §3 over the adjacent-brace cases: `{{#let x={a=1}}}`,
  `{{#let x={}}}`, and the nested `{{#let x={a={b=1}}}}}` (five trailing braces). Each must
  tokenize with the tag span fixed by width detection *before* the interior is scanned. No corpus, no
  merge — this is the construct's highest-risk surface. (ADR-025 adds the bracket cases.)
* *`check:hbs-conformance`* — already in `npm test`. Catches any ClassicBars regression from the `49/50`
  byte-identical line. If `let`/`{…}` ever bleed into the ClassicBars surface parser, the next run of this
  gate flags it. (Unlike ADR-025, this ADR adds no prelude helper, so there is no catalog/conformance
  churn here.)
* *ClassicBars isolation (realized).* The plan named `check:isolation`, but that gate is dependency-scoped
  (ADR-003/008). The MaxBars-only-surface guarantee is instead pinned where the diagnostics live: the
  ClassicBars `let-rejected-*` unit tests (a ClassicBars `{{#let …}}` is a located `DisallowedShape` at render —
  `checkSurfaceStrict`), and `check:dialect-diagnostics` (the LSP flags it in the editor). A `{name: …}` /
  `[…]` literal needs no separate assertion — `{`/`[` is a lex error in ClassicBars before the desugar.
* *Linter round-trip* (`Linter.Lower`) — pins that `{{#let a=1}}` lowers to
  `{{#let (bind "a" 1)}}` and `{b=1 c=2}` lowers to `(dict b=1 c=2)`. One canonical RawBars
  form per construct — no AST drift, no two-way sugar.

### Linter

* New hint *`prefer-let-over-with-as`* (MaxBars only): suggest `{{#let n=x}}…{{/let}}` when the
  body of a `{{#with x as |n|}}…{{/with}}` never uses bare names — the exact case where the
  forms are equivalent. *Soundness boundary:* the scope-chain rule (§1) means a partial invoked in the
  body inherits the re-rooted context and may consume bare names *invisibly* — and a host-supplied
  partial cannot be analysed at all. So the hint fires *only when the body invokes no partial*
  (`{{> …}}`, `{{#> …}}`, `{{yield}}`); a body that calls a partial is left alone
  rather than risk a rewrite that changes rendering. The genuine `with` use-cases (re-root with no
  alias, or re-root + alias with a bare-name body) are untouched.

### Editor tooling (ADR-017 contract)

The token vocabulary gains two new tag-body tokens, scoped to the MaxBars grammar variant: `{` and `}`
(the dict literal's delimiters). The LSP semantic-token emitter, the TextMate fallback grammar, and the
VS Code / JetBrains extension grammars each receive a one-time update; the *contract source*
([ADR-017](/adr/adr-0017-editor-support-lsp/) token-vocabulary.json) is the single edit point. (ADR-025
adds the `[`/`]` tokens, including the `[` dual-context disambiguation.)

### Documentation

* `maxbars.adoc` gains a `Let` section and a `Dict literal` section.
* `rawbars.adoc` adds one paragraph: the explicit `(bind …)` form is the desugared canonical;
  surface sugar lives in MaxBars.
* `classicbars.adoc` is *not* modified. The existing convention rule in `tutorials/src/classicbars.mjs`
  (*"No MaxBars operators"*) gains a parallel line: *"No MaxBars block-scoped bindings, no MaxBars dict
  literals."*

### Non-goals (deliberately deferred)

* *File-level front matter* (template-scoped data via a `---` YAML header). A host-layer concern (see
  the front-matter debate notes); `let` is the engine-side, lexically-scoped answer. If a front-matter
  adapter ships later it should *desugar at the host* into a top-level `let` — keeping one canonical
  binding mechanism.
* *Dropping `{{#with}}`* in MaxBars/RawBars. Considered and rejected — the carve-out cost exceeds the
  gain, and the philosophical objection (`with` re-roots ⇒ "hidden variable") already coexists with
  `{{#each}}`'s identical re-rooting. The linter hint covers the cases where `let` would actually
  read more clearly.

## Resolved during review

The team review of 2026-06-04 closed the questions that were previously left open or mis-scoped:

* *The list literal was split out to [ADR-025](/adr/adr-0025-list-literal/).* It alone needs a new
  `list` constructor in the *shared* prelude (the prelude has no list constructor today), so it carries a
  catalog + conformance blast radius that `let` and the dict literal do not. Keeping them in one ADR
  conflated "pure MaxBars surface" with "shared-prelude change"; the split makes each decision honest and
  lets `let` + dict ship first.
* *Kernel primitive: a dedicated `Let [(name, expr)] body` AST node*, not a sugar that lowers to a chain
  of single-binding scope-frame ops. The runtime behaviour is identical, but the `Linter.Lower`
  round-trip is a *stated gate* (see *Consequences*), and it cannot be specified without fixing the
  canonical form: a dedicated node round-trips one-to-one, whereas the sugar-chain lowers
  `{{#let a=1 b=2}}` to *nested* `(bind)` blocks — two-way drift, the exact failure the gate
  exists to prevent. So the node is the canonical form.
* *Binding semantics are sequential* (§1), not parallel-in-the-enclosing-scope. The dedicated node makes
  forward reference (`b` sees `a`) free, and it matches every author's mental model of `let` while
  staying a single total walk.
