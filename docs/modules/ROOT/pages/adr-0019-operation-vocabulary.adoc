= ADR-019: The operation model — "operation" / "definition" natively, "helper" at the host boundary
:navtitle: ADR-019 Operation vocabulary

*Status:* Accepted — *implemented*. The `Helper` → `Operation` rename landed in one gated commit
(build + `test:compile` byte-identical + `check:catalog` + `check:bundle`); the `concepts` §1 reframe and
`#glossary` are in place; the host API keeps the frozen `helper` word; and `check:glossary` gates the two
registers' agreement. The conditions below (frozen boundary, single gated rename, owned kind taxonomy)
are met. *Date:* 2026-06-02. Builds on
xref:concepts.adoc[the core model] §1–4 (everything is an application; there are *no variables*; the head
is always a name; scope is install/remove of names) and
xref:adr-0001-structural-parser-and-walker.adoc[ADR-001] (the meaning plug-in). Constrains, but does not
revert, xref:adr-0018-user-defined-helpers.adoc[ADR-018] (`registerHelper`). This record is about
*naming*, not mechanism: the mechanism is fixed; what we *call* it in the native dialects has been wrong.

== Context

FlatBars inherited the word *helper* from *Handlebars* — not Mustache. Mustache has no helpers: it is
"logic-less," and its only extension point is an in-data *lambda*. *Helper* is a Handlebars coinage —
`Handlebars.registerHelper`, and the built-ins `if` / `each` / `with` / `unless` / `lookup` that
Handlebars itself calls helpers. In Handlebars the word is honest: it has real variables (a
`pass:[{{name}}]` is a path lookup), and a *helper* is the bolt-on for when a path is not enough — the
auxiliary that *helps* the real content. That is the sense the team objects to: helper as *subordinate*.

In FlatBars that sense is a falsehood. xref:concepts.adoc[concepts] §1 is explicit: there are *no
variables*; `pass:[{{{city}}}]` *calls* the operation `city`. The thing the `{{ }}` family treats as an
afterthought is, here, the entire language. Keeping "helper" as the native noun imports an ideology
(logic-less-template-plus-escape-hatch) that §5 ("no keywords — not even `else`") already rejects, and it
*hides the one genuinely new thing the model says*.

That new thing is a dissolution. The `pass:[{{ }}]` family splits its extension story across *two*
languages and *two* mechanisms:

* a *lambda* (Mustache), a function placed *in the data*, invoked when its name resolves at a leaf;
* a *helper* (Handlebars), a function registered *on the side*, applied to a block or an interpolation.

This is a *binding-site* distinction: in-data vs registered. FlatBars has *one* binding site — the
operation environment (§4). A Mustache lambda-at-a-leaf is just a *nullary operation installed in scope*
(by a block or the host); a Handlebars block helper is just a *block operation*. One axis, not two.
"Helper" buried this; a truer noun should advertise it.

The countervailing force is migration. xref:host-api.adoc[host-api] §7.4 is a deliberate
Handlebars→FlatBars dictionary, and ADR-018 *just* shipped `registerHelper` because "Handlebars-faithful
without it is faithful to the grammar and unfaithful to the workflow." Renaming the word a migrator types
spends the adoption capital ADR-018 was paid to build.

== Decision

. *Two registers, split by audience.*
+
** *Native conceptual register* — xref:concepts.adoc[concepts] and the RawBars / MaxBars dialect docs,
   *and the internal code identifiers*. The primary noun is *operation* (the thing a name invokes at a
   call site); the thing *installed in the environment* is a *definition*. A name *resolves* to a
   definition in the current *scope*; applying it is an *operation*.
** *Boundary / compatibility register* — the JS host facade. `renderWith` and the source-level
   `registerHelper` affordance (ADR-018) and the §7.4 migration table *keep the word "helper,"*
   documented as: a *helper is how a host registers an operation*. The migrator never loses the term;
   the newcomer never inherits the lie. *This boundary word is frozen* — `helper` is the permanent
   migration anchor ADR-018 paid for, and is never renamed even as the internals become `Operation`;
   that frozen boundary is what makes the rename below safe. (There is no `compileWith`: compilation is
   helper-agnostic — it emits `rt.call`, bound at run time — see ADR-018.)

. *Operations have two kinds, the contract already forces them.* The type
  `Ctl m env -> Array Value -> m Value` (xref:host-api.adoc[host-api] §7.3) distinguishes *inline*
  operations (ignore the control handle) from *block* operations (use it). *Values* are not a third kind:
  a value is a *nullary inline operation* — there being no variables, that is the only way a value appears.

. *Rename the internal type `Helper` → `Operation`.* The kernel/fullbars/compile `Helper` type, the
  prelude table, and the schema's kind language (`inline` / `block`, arity) read as operations and
  definitions. The JS-facing `registerHelper` and the rest of the `flatbars-js` facade are the *explicit
  exception* — they stay, by Decision 1.

. *MaxBars gets a surface gloss, not a new model.* The infix symbols `+ >= |` are *operators* (surface
  sugar); prefix heads and pipe stages are *operations*. We keep the entrenched word "operator" rather
  than coin a replacement — but because *operator* and *operation* differ by one letter, every use must
  carry the contrast: an **operator is surface sugar that desugars to an operation** (never standalone).
  The glossary pairs them on one line for exactly this reason. There is *no "function"* —
  xref:concepts.adoc[concepts] §3 forbids callable values, so "function" would promise first-class
  functions the language does not have. Both desugar to the same core `App`
  (xref:concepts.adoc[concepts] §8), so the two surface words sit over one core, exactly as "one parser,
  four languages / one compiler" already claims.

. *Say the dissolution out loud.* xref:concepts.adoc[concepts] §1 gains one sentence: FlatBars has no
  logic-less core for an operation to be an *escape hatch from* — application *is* the language, so an
  operation is not a "helper" in the subordinate sense; and a glossary records
  *operation / definition / scope / inline / block / operator* each with its host-API synonym.

== Consequences

* *A deliberate, documented asymmetry*: the internal type is `Operation`, the host registrar is
  `registerHelper`. This is the cost of keeping ADR-018's migration value while telling the native model's
  truth. It is ratified here so a contributor meeting `registerHelper : … -> Operation` reads it as intent,
  not drift.
* *A new normative glossary* (xref:concepts.adoc[concepts] or a `glossary.adoc`) becomes the single
  teachable artifact for the two registers — and it is *gated*, not prose-on-trust: a `check:` (mirroring
  `check:catalog`) asserts that every native term carries its host-API synonym and that the
  xref:host-api.adoc[host-api] §7.4 migration table and the glossary agree on the
  operation↔helper / definition / scope / inline / block / operator mapping. A drift in either fails the
  build, so the two registers cannot silently diverge. The gate checks *terms*, not prose, to avoid a
  maintenance tax.
* *This ADR owns the kind taxonomy.* The single, shared set of operation kinds is *value* (a nullary
  inline operation), *inline* (n-ary), *block*, and *operator* (the MaxBars surface form). ADR-018's
  declared arities and xref:adr-0017-editor-support-lsp.adoc[ADR-017]'s catalog-driven completion both
  *reference* this taxonomy rather than coining their own labels. (Note: the kind is *inline*, not
  "transform" — "transform" is the Lab's JSONata data-preprocess and must not be overloaded as a kind.)
* *The `Helper` → `Operation` rename is wide and mechanical* across kernel / fullbars / compile and the
  schema language, and lands in *one* commit gated by a hard checklist, all green:
+
--
  . `npm run build` — every package compiles under the new type name;
  . `npm test` — full suite, including `npm run check:catalog` (the catalog prose shifts with the prelude
    vocabulary, so `npm run gen:catalog` is regenerated in the same commit);
  . `npm run test:compile` — *byte-identical* compiled-vs-interpreted output, proving the rename is purely
    nominal (no semantics change);
  . `npm run check:bundle` — the editor bundle tracks the renamed source.
--
+
The boundary word `helper` (Decision 1) does *not* move in this commit — only the internal `Operation`
type, the prelude/schema kind language, and `concepts`/dialect prose.

== Alternatives rejected

* *Keep "helper" everywhere.* Maximizes familiarity, but cements the falsehood in the native model and
  leaves the lambda/helper dissolution unsaid — the very insight that distinguishes FlatBars from the
  family it parses.
* *Rename to "function."* Vetoed by xref:concepts.adoc[concepts] §3: nothing produces a callable value and
  `Value` is free of functions. "Function" would set an expectation the language exists to deny.
* *"Word" / Forth dictionary framing.* Most honest to the model (scope *is* a dictionary, §4), but opaque
  to the `{{ }}`-family audience the dialects are for. Retained as *explanatory* framing in prose, not as
  the surface noun.
* *Docs-only reframe (leave code as `Helper`).* Considered and rejected by the team: a `concepts`/dialect
  vocabulary that the type names contradict trains contributors back into "helper." The rename is the
  cost of coherence.
* *Open custom block operations to make the model fully uniform.* Out of scope and orthogonal —
  ADR-018 defers custom *block* helpers for a compile-equivalence reason; this ADR only renames what
  exists.

== Open questions

* *Schema kind labels* — *resolved* (see Consequences): the taxonomy is *value* / *inline* / *block* /
  *operator*, with `value` derived from `inline` + arity 0 internally and surfaced as its own label to
  the catalog/LSP. "transform" is explicitly *not* a kind (it is the Lab's data-preprocess).
* *Naming `definition` vs `binding` for the environment entry.* "Definition" reads well in prose;
  "binding" is more precise about the name↔meaning pairing. This ADR picks *definition*; revisit if the
  glossary proves it ambiguous against block-installed scope.

== Addendum: host-registered block operations for RawBars and MaxBars (design)

*Status:* Accepted (team-reviewed). Reopens the *"open custom block operations"* alternative this ADR
deferred — now unblocked, because xref:adr-0020-user-block-helpers.adoc[ADR-020] built the block-operation
machinery (the `Engine.blockArgs` seam, `Ctl.hash`/`blockParams`, the `rt.block` channel, and a JS
marshaller) and proved it byte-identical across interpreter and compiler. Only one dialect (FullBars) wired
a host registrar to it. This addendum extends host registration to *RawBars* and *MaxBars*, and settles
what they expose and what they call it.

The review's conditions, folded in: the registrars use *operation* (never `helper`) for the native
dialects (Dana); there is *no* `compileWithOperations` — compilation stays operation-agnostic, emitting
`rt.call` bound at run time, exactly as ADR-018 set up (Lena); and the `test:compile` harness must register
operations through each dialect's compile + render path so the new cases gate *both* paths (Priya).

=== The vocabulary fork (resolved)

ADR-018 shipped `renderWith` / `registerHelper` for FullBars; Decision 1 above froze *helper* as that
facade's boundary word — the *Handlebars-migration anchor*. The fork: when RawBars and MaxBars gain a
registrar, is the boundary word still *helper*, or *operation*?

*Decision: the boundary word is dialect-scoped, not global.* FullBars keeps `renderWith` / `registerHelper`
— it is the Handlebars-faithful surface, and "helper" is the migrator's term it was paid to keep. RawBars
and MaxBars are *native* dialects with no Handlebars-migration debt — RawBars is the very dialect that
*rejects* the helper framing (concepts §1) — so their registrars use the native noun: a host registers an
*operation*. The frozen "helper" of Decision 1 is thereby scoped to *FullBars' facade* (the anchor it was
created for), not imposed on dialects that never had it. This keeps each facade honest to its own dialect's
register and is exactly the two-register model applied at the boundary, not just in the docs.

=== What each dialect exposes

* *RawBars* — `renderWithOperations(operations, partials, template, data)` (and the source-level
  `registerOperation(name, fn[, arity])` affordance, mirroring `registerHelper`). RawBars is the
  meaning-free core: it has *no surface sugar*, so a block head emits no `@hash`/`@param` markers — a
  RawBars block operation therefore gets `options.fn`/`options.inverse` (and `options.fn(ctx, { data })`
  for scoped vars) but *no* `options.hash` and no `as |…|` block params (there is no surface to write
  them). Resolution stays *strict* — an unknown operation is `UnknownHelper`, never `blockHelperMissing`
  (RawBars has no implicit-section policy; ADR-020's lenient resolve is FullBars/MaxBars only).
* *MaxBars* — `renderWithOperations(...)` over the MaxBars surface (infix/pipes/loop vars). Because MaxBars
  *is* FullBars' surface plus operators, it desugars the same `@hash`/`@param` markers, so a MaxBars block
  operation gets the *full* surface: `fn`/`inverse`/`hash` + `options.fn(ctx, { data, blockParams })`, and
  the lenient `blockHelperMissing` resolve it already inherits.

=== Mechanism — reuse, do not rebuild

The kernel already supports all of this; the work is two thin facades plus marshalling, no new engine
machinery:

* The JS marshaller that turns a host function into an `Operation` (inline *or* block, usage-decided, with
  `options.hash`/`fn`/`inverse` + the `{ data, blockParams }` frame) is *dialect-agnostic* — `FullBars.JS`'s
  `mk` is lifted to a shared helper and reused by all three registrars.
* RawBars renders through the *strict* `runResolved` (registering the operations into the env via
  `registerAll`); MaxBars through the *lenient* `runResolvedLenient` with `maxOptions` + `maxLoopVars`, the
  same path `renderMax` already uses. Each gets a `…WithOperations` entry in its package, surfaced on the
  `flatbars-js` facade.
* `Ctl.hash`/`blockParams` are populated by the shared `blockArgs` seam regardless of dialect; RawBars sees
  `Nothing`/`[]` (no markers), MaxBars sees them — so the *same* marshaller yields the per-dialect surface
  above with no per-dialect branching.

=== Gating

* `test:compile` gains RawBars and MaxBars block-operation cases (interpreter ≡ compiled), mirroring the
  FullBars `block:*` cases — RawBars covering `fn`/`inverse`/`data`, MaxBars also `hash` + block params.
* `check:glossary` extends to record the second boundary spelling: *operation* is the RawBars/MaxBars host
  registrar's word, *helper* the FullBars one — both naming the same `Operation`. The gate keeps the
  glossary and the facade in step (a registrar named against the wrong register fails the build).
* Docs: the RawBars and MaxBars dialect pages document `renderWithOperations`; the FullBars ADR-020 line
  that read "RawBars/MaxBars use the operation vocabulary, not `registerHelper`" is now precise — they use
  `registerOperation`, the native-boundary twin.

=== Out of scope (this addendum)

* A *new MaxBars-native block spelling* (a pipe/infix block form) — operators stay surface sugar over the
  same `App`; `pass:[{{#op …}}]` is the block form for every dialect.
* `options.ids` / source locations — still throw by design (ADR-020), in every dialect.
