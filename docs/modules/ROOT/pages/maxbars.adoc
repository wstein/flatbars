= The MaxBars dialect (infix operators & pipes)
:hbs: Handlebars

MaxBars is the top of the dialect ladder — **RawBars ⊂ FullBars ⊂ MaxBars**. It
is FullBars plus a richer *surface*: infix operators and pipes. Everything below
the surface is reused unchanged.

== Reuse by dependency

MaxBars desugars to the same core `Expr` that FullBars already understands, so it
reuses FullBars *wholesale by dependency* — the engine, prelude, value policy,
surface desugar, **and the compiler**. The only new piece is the interior
expression grammar, plugged in through the `ParseOptions.parseExpr` seam
(xref:grammar.adoc[]); the structural tree-builder stays grammar-agnostic.

[source,purescript]
----
maxOptions   = defaultParseOptions { parseExpr = MaxBars.Expr.parseMaxExpr }
renderMax    = renderSurfaceDiagWith maxLoopVars maxOptions  -- FullBars engine, reused
compileMaxJs = compileSurfaceWith   maxLoopVars maxOptions  -- FullBars compiler, reused
----

The second seam, `maxLoopVars`, is a `LoopVars` resolver the surface desugar
consults; MaxBars wraps `noLoopVars` with `reservedScope` to turn on the *reserved
variable model* (below) — `loop`/`root`/`parent` as scope-declared names. FullBars
passes `noLoopVars`, keeping `@`/`pass:[../]` and leaving bare names as data paths.

A shared semantic *kernel* (truthiness/stringify/escape, frame mechanics) is
extracted lazily — only for proven overlaps, never a vague `common` package.

== Operators

Operators desugar to plain core helper calls — the same `App` nodes a `(and a b)`
subexpression produces — so the prelude, engine, and emit rules need no changes.

[cols="1,1,2",options="header"]
|===
|Infix |Helper |Example → core

|`&&` |`and` |`pass:[{{ a && b }}]` → `pass:[(and a b)]`
|`\|\|` |`or` |`pass:[{{ a \|\| b }}]` → `pass:[(or a b)]`
|`!` |`not` |`pass:[{{ !a }}]` → `pass:[(not a)]`
|`==` `!=` |`eq` `ne` |`pass:[{{ x == 1 }}]` → `pass:[(eq x 1)]`
|`<` `>` `<=` `>=` |`lt` `gt` `lte` `gte` |`pass:[{{ x >= 18 }}]` → `pass:[(gte x 18)]`
|`+` `-` `*` `/` `%` |`add` `subtract` `multiply` `divide` `modulo` |`pass:[{{ price * qty }}]` → `pass:[(multiply price qty)]`
|`??` |`coalesce` |`pass:[{{ a ?? b }}]` → `pass:[(coalesce a b)]` (first non-null)
|`\|` (pipe) |application |`pass:[{{ a \| f x }}]` → `pass:[(f a x)]` (piped value first)
|===

Precedence (loosest → tightest): pipe, `??`, `||`, `&&`, comparisons
(non-associative), additive (`+` `-`), multiplicative (`*` `/` `%`), prefix `!`,
then application/atom — so `pass:[{{ n + 1 > 5 }}]` is `pass:[(gt (add n 1) 5)]`.
Pipe chains are left-associative: `pass:[a | f | g]` ⇒ `pass:[(g (f a))]`. Paths,
literals, and `(parenthesised)` subexpressions are exactly as in FullBars.

The operator characters are excluded from the identifier set so they tokenise as
operators — but this is a *MaxBars-only* lexer mode (`ParseOptions.lexOptions`
`infixArith`): RawBars/FullBars keep `+ - * / ?` as path/name characters, so
`../x`, `a/b`, and `partial-block` are unaffected. `.` and `@` stay identifier
characters in **every** dialect, so a dotted path like `price.net` is still one
path even in MaxBars (and `/` is therefore unambiguously division). Arithmetic is
strictly numeric — a non-number operand is a `TypeError` (no coercion) — and `??`
is *null*-coalescing (a present `0`/`""`/`[]` wins), independent of the file's
`@truthiness` mode.

== The variable model

MaxBars has *no bare loop variables* and *no `@` namespace*
(xref:adr-0021-maxbars-variable-model.adoc[ADR-021], superseding ADR-006). A bare
`pass:[{{first}}]`/`pass:[{{length}}]` is an ordinary *data field*. Loop state, the
enclosing context, and the root are read through five reserved, chainable scoped
names — `this` / `loop` / `root` / `parent` / `outer`:

[cols="1,3",options="header"]
|===
|Name |Reads

|`this` |the current context (`pass:[{{this}}]`, `pass:[{{this.name}}]`).
|`loop` |the *current loop* object: `loop.index0`/`index1`/`rindex0`/`rindex1`/
  `length`/`first`/`last`/`key`/`this`. Chains over enclosing loops:
  `pass:[{{loop.parent.index0}}]`, `pass:[{{loop.parent.parent.length}}]`,
  `pass:[{{loop.root.length}}]`.
|`outer` |a *named* enclosing loop's object — any `pass:[label NAME]` clause
  (xref:adr-0013-labelled-loops.adoc[ADR-013]); same shape as `loop`.
|`parent` |the *enclosing context*: `pass:[{{parent.name}}]`, chained
  `pass:[{{parent.parent.name}}]`.
|`root` |the *root context*: `pass:[{{root.title}}]`.
|===

The index arithmetic is normative (`rindex0 = length − 1 − index0`,
`first = index0 == 0`, …), and the objects are immutable per-iteration snapshots —
the interpreter and compiler build the identical object, so they agree by
construction. `@root` becomes `root`, `pass:[../x]` becomes `parent.x`, and an
`@`-prefixed name is a *located parse error* pointing at this model.

[source,handlebars]
----
{{#each items}}{{loop.index1}}/{{loop.length}}: {{this.name}}{{#unless loop.last}}, {{/unless}}{{/each}}

{{#each rows}}{{#each this}}{{loop.parent.index0}}.{{loop.index0}} {{parent.label}} {{root.title}}{{/each}}{{/each}}
----

== The block-partial body (`yield`)

Inside a block partial — `pass:[{{#partial "name"}}…{{/partial}}]` or the
Handlebars block-partial sigil `pass:[{{#> name}}…{{/name}}]` — the caller's body
is rendered by the reserved name **`yield`**:

[source,handlebars]
----
{{!-- the "layout" partial --}}    <main>{{yield}}</main>
{{#partial "layout"}}<p>hi</p>{{/partial}}    {{!-- → <main><p>hi</p></main> --}}
----

`yield` is the hyphen-free, cross-dialect spelling of Handlebars'
`pass:[{{> @partial-block}}]`, which MaxBars cannot use: the `@` sigil is reserved,
and a bare `partial-block` would lex as the subtraction `partial - block`. One
scoped operation, reached one way per dialect:

[cols="1,2",options="header"]
|===
|Dialect |Spelling

|MaxBars |`pass:[{{yield}}]`
|RawBars |`pass:[{{{yield}}}]`
|{hbs} / FullBars |`pass:[{{> @partial-block}}]`
|===

The body is already-rendered, escape-safe output (a `VSafe` value), so MaxBars'
`pass:[{{ }}]` auto-escape is a no-op on it — `pass:[{{yield}}]` and
`pass:[{{{yield}}}]` emit identical bytes.

`yield` is reserved like `this`/`loop`/`root`/`parent`: a same-named data field is
shadowed (read it with an explicit `pass:[{{lookup this "yield"}}]`), and a loop
`pass:[label yield]` is flagged by the MaxBars lint.

== Block conditions

A block *open* parses its head as the helper name followed by arguments, each a
full infix expression — so a condition needs no parentheses:

[source,handlebars]
----
{{#if x > 0 && x < 10}}in range{{/if}}      {{!-- = {{#if (and (gt x 0) (lt x 10))}} --}}
{{#unless a || b}}neither{{/unless}}
----

This is the core `parseHead` seam: only block opens use it. A *clause* separator
still takes a parenthesised condition — `pass:[{{elif (a && b)}}]`,
`pass:[{{else if (a && b)}}]` — because separators share their tag shape with
output expressions.

== Block parameters

Block parameters work as in FullBars — a trailing `pass:[as |a b|]` binds scoped
names over the block body:

[source,handlebars]
----
{{#each xs as |item i|}}{{i}}: {{item}}{{/each}}
{{#with user as |u|}}{{u.name}}{{/with}}
----

The head argument grammar omits the *pipe* rung, so a bar in head position is
**structure** — the block-parameter delimiter — not the pipe operator. The clause
is carried untouched to the same surface desugar FullBars uses
(xref:surface.adoc[§5.5]); MaxBars adds no machinery of its own. The consequence
is the one head-position rule below: to *pipe* a block argument, parenthesise it,
which re-enters the full expression grammar.

[source,handlebars]
----
{{#each (people | reverse) as |p|}}{{p.name}}{{/each}}
----

== Labelled loops

A trailing `pass:[label NAME]` clause (xref:adr-0013-labelled-loops.adoc[ADR-013])
names the loop's *frame*, so an inner body can read the **enclosing** loop's full
state — not just its element. `outer` is the named twin of `loop` (same object
shape); it binds the frame reified as an object whose fields are the loop
variables (`index0`/`first`/`length`/…):

[source,handlebars]
----
{{#each rows as |row| label outer}}
  {{#each row}}{{outer.index1}}/{{outer.length}}: {{this}}{{#if outer.first}} (first row){{/if}}
  {{/each}}
{{/each}}
----

`outer` exposes `this` / `index0` / `index1` / `rindex0` / `rindex1` / `first` /
`last` / `length` / `key` — the same values, and the same normative arithmetic, as
the bare loop variables of that loop. It is an *immutable per-iteration snapshot*,
reached by ordinary path lookup (`pass:[{{outer.length}}]`), so the interpreter and
compiler agree by construction. A label and block params compose:
`pass:[{{#each rows as |row| label outer}}]` binds both `row` (the element) and
`outer` (the frame).

Notes:

* The label object names *one* loop and carries no `parent` field — to reach two
  enclosing loops, label both (no `pass:[../]` climbing).
* Choosing a *reserved root* as the label — `pass:[label this]` / `loop` / `root` /
  `parent` / `yield` — shadows that name for the body; the MaxBars lint warns and
  suggests a fresh name.
* `label` is a surface-desugar feature on `each`, so FullBars accepts it too; only
  the bare-loop-variable *vocabulary* is MaxBars-only.

== Host-registered operations

`renderWithOperations` renders MaxBars source against a bag of host-supplied
*operations* (ADR-019 addendum) — the native boundary word for what FullBars
calls a *helper* (`renderWith` / `registerHelper`). It is the same marshaller and
runtime; only the dialect surface and the vocabulary differ.

[source,purescript]
----
renderWithOperations
  :: Array (Tuple String (Operation (Either Error) (RefEnv (Either Error))))
  -> Array (Tuple String String)   -- partials (MaxBars source)
  -> String -> Value -> Either String String
----

A *block* operation receives a Handlebars-style `options`: `options.fn(ctx)`
renders the body (shifting context), `options.inverse(ctx)` the `pass:[{{else}}]`
clause, `options.hash` the surface `k=v` arguments, `options.fn(ctx, { data })`
supplies scoped `@vars`, and `options.fn(ctx, { blockParams })` binds the names
declared by a trailing `pass:[as |a b|]`. MaxBars is *lenient* (it inherits the
`blockHelperMissing` resolve), so an unknown head falls through rather than
erroring.

From a JS host, `renderMaxWith(operations, partials, template, data)` marshals
plain functions into these operations (the FlatBars Lab and `flatbars-js`).

== v1 limitations

* **Clause separators need parenthesised conditions** — `pass:[{{elif (a && b)}}]`
  / `pass:[{{else if (a && b)}}]`, since `pass:[{{ … }}]` separators and output
  share a tag shape. Block opens (`pass:[{{#if a && b}}]`) do not.
* **A pipe in a block head must be parenthesised** — `pass:[{{#each (xs | f) …}}]`,
  not `pass:[{{#each xs | f}}]`. The head grammar omits the top-level pipe rung so
  a bar can serve as the `pass:[as |x|]` block-parameter delimiter; an
  unparenthesised top-level bar in a head is therefore treated as structure, not a
  pipe (the same way FullBars and the core parser treat it).

== Truthiness

MaxBars shares FullBars' truthiness, including the per-file `@truthiness`
directive (xref:directives.adoc[]). A reader can rely on `pass:[{{#if x}}]` and
`pass:[{{ x && y }}]` always agreeing within one file, because both consult the
file's falsy set.
