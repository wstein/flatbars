= ADR-020: User-defined block (section) helpers (FullBars)
:navtitle: ADR-020 User block helpers

*Status:* Accepted (v1 scope set by team review — see Decision). *Date:* 2026-06-02. Extends
xref:adr-0018-user-defined-helpers.adoc[ADR-018] (user helpers, inline-only) by lifting the one limit it
stated: custom *block* helpers. Builds on xref:adr-0011-compile-to-js.adoc[ADR-011] (compile ≡ interpret)
and the `blockHelperMissing` work (xref:fullbars-compat.adoc[]), which is what makes this now feasible.

== Context

ADR-018 shipped inline user helpers and *deferred* block helpers with a stated reason: the compiled
runtime's `rt.block` "refuses every block helper except the internal `apply`, so a custom block helper
could never satisfy compile ≡ interpret without generic block emission the emitter does not have."

*That blocker is gone.* Closing the Handlebars `blockHelperMissing` gap required exactly that generic
path: the emitter already emits `pass:[rt.block(name, args, frame, bodyFn, clauses)]` for *any*
non-lowered block head, and `rt.block` now dispatches an unregistered head as a data section
(`each`/`with`/inverse). So the compiled side already *carries the block body as a callback* (`bodyFn`)
and the `{{else}}` clause (`clauses`). What is still missing is only a branch that hands those to a
*user* function. The interpreter never had the blocker at all: `Operation m env = Ctl m env -> Array
Value -> m Value`, and `Ctl` already exposes `children`, `render`, and `clause`
(xref:adr-0001-structural-parser-and-walker.adoc[ADR-001]) — `if`/`each`/`with` *are* block operations,
and `renderSurfaceWithHelpers` already accepts `Operation`s at the PureScript level. The gap is the *JS
boundary* (`buildHelpers` marshals `(args) ⇒ value` — inline only) and the *compiled* user branch.

Three facts scope the decision:

. *Block operations are a kernel capability, not a per-dialect feature.* RawBars/FullBars/MaxBars share
  the engine, so the interpreter already runs any registered block operation. The new work is the JS
  *host* affordance (`registerHelper`) plus its compiled twin.
. *MinBars is a peer engine whose sections dispatch on the data value.* A Mustache "section lambda" is a
  *function in the data* — precisely what `Value` deliberately is not (xref:concepts.adoc[]; the
  conformance stance in xref:adr-0007-minbars.adoc[ADR-007]). Adding MinBars section helpers would
  reintroduce `VFunction` or bolt a non-standard registry onto a Mustache-fidelity engine. Out of scope.
. *The Handlebars workflow is the target.* The clone goal (xref:fullbars-compat.adoc[]) means the API is
  Handlebars': a block helper is a registered function that receives an `options` object with `fn`
  (render the body) and `inverse` (render `{{else}}`). "Paste your Handlebars block helper and it runs"
  is the bar.

== Decision

. *`registerHelper` block helpers are FullBars-only; RawBars and MaxBars do not get them.* The kernel
  block-operation *capability* is dialect-agnostic (it already runs any `Operation` seeded at the
  PureScript level), but `registerHelper` is the *FullBars* JS affordance — the Handlebars-compat boundary
  word (ADR-018). RawBars and MaxBars use a *different concept and terminology* — *operations* /
  *definitions* per xref:adr-0019-operation-vocabulary.adoc[ADR-019] — so they get *no* `registerHelper`,
  and their facades (`render`, `renderMaxbars`) deliberately take no helpers bag. A native MaxBars
  block-operation registration is ADR-019's concern, not this one. MinBars section helpers are *not*
  provided either — its sections are function-in-data, which `Value` does not model, and faking it would
  regress ADR-007's conformance posture. So this ADR adds the JS-source block-helper path and its compiled
  twin to the *FullBars* facade (`renderWith`) alone.

. *One registration; usage decides block vs inline (Handlebars-compatible).* `registerHelper(name,
  fn[, arity])` is unchanged. The engine passes a trailing `options` object whenever the call site is a
  block (`pass:[{{#name …}}…{{/name}}]`); `options.fn` is present only then. A helper used inline
  (`pass:[{{name …}}]`) sees no `fn`. No separate `registerBlockHelper` — a second primitive would break
  the paste-compatibility the clone goal rests on.

. *The v1 `options` surface is `fn` and `inverse` — and only those.*
+
[source,js]
----
registerHelper("list", (items, options) =>
  safe("<ul>" + items.map((i) => "<li>" + options.fn(i) + "</li>").join("") + "</ul>"));
// {{#list people}}{{name}}{{/list}}
----
+
  * `options.fn(ctx[, { data }])` renders the block body with `ctx` as the new context (called with no
    argument ⇒ the current context, matching Handlebars `options.fn(this)`). The shift changes only the
    context: the body *inherits* the enclosing scope — `pass:[{{@index}}]`/`pass:[{{@key}}]`/`../`
    resolve as they would just outside the block (both paths build the shifted frame the same way: the
    interpreter's `pushFrame Map.empty ctx` and the compiled `{ …frame, ctx }`). The optional second
    argument's `data` object (Handlebars' runtime-options `data` frame) *adds scoped `@vars`* layered over
    the inherited scope — `options.fn(x, { data: { index: i, first: i === 0 } })` makes
    `pass:[{{@index}}]`/`pass:[{{@first}}]` available in the body. Keys map uniformly (interpreter: a
    pushed frame of constant helpers; compiled: layered `binds`, which `rt.call` checks first), so standard
    and custom keys behave identically — gated by conformance cases (Phase 2, *done*).
  * `options.inverse(ctx[, { data, blockParams }])` renders the `{{else}}` clause (empty string if none).
  * `options.hash` is the surface `k=v` object (`{}` when none) — *Phase 3, done* (see the addendum).
  * Block params (`pass:[{{#list xs as |item idx|}}]`) bind via `options.fn(ctx, { blockParams: [v0, v1] })`:
    the declared names ride the `Ctl`/emit channel and bind to the supplied values in the body —
    *Phase 3, done*.
  * Only `ids`/`loc`/`lookupProperty` *throw* a located error ("not supported in a FlatBars block helper")
    rather than returning `undefined` — a loud partial cannot become a silent conformance lie.

. *Return escaping branches on usage* (one `fn`, two wrappings). Used *inline* (`pass:[{{name …}}]`), the
  return is an *escaped* `VString` unless `safe(…)` (ADR-018, unchanged). Used as a *block*
  (`pass:[{{#name}}…{{/name}}]`), the return is `VSafe` (raw) — matching Handlebars, which treats block
  output as already-safe HTML assembled from already-escaped sub-renders. `options.fn`/`inverse` return
  already-escaped body text. A thrown JS error becomes a located render/compile error (ADR-018).

. *Dual-mode through one marshalling, gated byte-for-byte.* The interpreter's existing JS-helper
  marshaller becomes `Ctl`-aware (one path, not two): it always appends `options`, with `fn`/`inverse`
  present only when `ctl.children` is non-empty (block usage). To call *back* into the pure interpreter
  without throwing across the FFI, `options.fn`/`inverse` are backed by a PureScript callback returning
  `{ ok, value, error }` (run `ctl.render` over the main/`else` body with `pushFrame` for the context
  shift); the JS `options.fn` wrapper unwraps it and throws *in JS* on `!ok`, caught by the marshaller's
  existing `try/catch`. The compiler adds a `userBlockHelpers[name]` branch to `rt.block` that builds the
  *same* `options` from `bodyFn`/`elseFn`/`frame` and returns a `Safe`. `test:compile` is extended with
  block-helper cases — per `options.fn` call-count (0 / 1 / N renders), `inverse`, and return-escaping —
  so interpreter ≡ compiled is proven, not assumed.

. *Arity counts positional arguments only.* `options` is never counted. A declared arity
  (`registerHelper(name, fn, 1)`) validates the positional args; the diagnostics match ADR-018's.

. *Terminology (xref:adr-0019-operation-vocabulary.adoc[ADR-019]).* Natively this is a *block
  operation*; at the JS host boundary it is a *block helper* (the frozen boundary word). Surface/concept
  docs say "block operation"; the JS API says `registerHelper`.

== Consequences

* `flatbars-js` block helpers work in both the interpreter and the compiled module; the FullBars
  Handlebars-conformance corpus's one block-helper miss (`pass:[{{#bold}}]`) flips to a pass
  (96% → ~98%), and `fullbars-compat.adoc` §3's "user-defined block helpers" roadmap item moves ☐ → ☑.
  The numbers are the acceptance test.
* The interpreter FFI grows by one call site (`callJsBlockHelperImpl`) and one wrapper
  (`jsBlockOperation`); the canonical PureScript `prelude`/engine are unchanged.
* `rt.block` grows a user-block branch beside the existing `apply` and `blockHelperMissing` arms; the
  block-body callback (`bodyFn`) and clause object it already receives are reused, so no new emit shape.
* New honest limits, documented in-source: the v1 `options` surface is `fn`/`inverse`/`hash` (the rest
  throw), and MinBars section helpers remain unsupported by design.

== Alternatives rejected

* *A separate `registerBlockHelper` / FlatBars-native block handle.* Cleaner separation, but it breaks
  "paste your Handlebars helper and it runs" — the whole point of the clone. One registration with a
  usage-decided `options` is the Handlebars model.
* *MinBars section helpers via function-in-`Value` or a registry fallback.* The first breaks the
  pure-data core; the second is non-standard Mustache. Both regress ADR-007. MinBars stays out.
* *The full Handlebars `options` surface in v1* (`data`, `blockParams`, `ids`, …). A large, drift-prone
  surface to keep interpreter ≡ compiled; ship `fn`/`inverse`/`hash` first and *throw* on the rest, so
  the gap is loud. Phase 2.
* *Do nothing (keep inline-only).* The block-helper case is the documented section-lambda path
  (xref:fullbars-compat.adoc[]) and a measured conformance miss; the `blockHelperMissing` work already
  paid the hard cost (generic block emission), so the remaining delta is small.

== Open questions

* *`options.data` — done (Phase 2).* `options.fn(ctx, { data })` supplies scoped `@vars` to the body,
  uniformly across interpreter and compiled paths (gated by `block:supplies-data`).
* *`options.hash` + block params — done (Phase 3).* Implemented via the `@hash`/`@param` marker channel
  designed in the addendum below: the surface marks a block head's hash and `as |…|` names, the kernel
  `blockArgs` seam (and the compiler, centrally) split them off the positional list into `Ctl.hash` /
  `Ctl.blockParams`, and the user marshaller routes them to `options.hash` and `options.fn(ctx, {
  blockParams })`. Built-ins, the catalog, and the meaning-free core are untouched. Gated by
  `block:hash` / `block:params` / `block:hash-params-data` + Lab unit tests.
* *RawBars / MaxBars block operations* — *delivered* under
  xref:adr-0019-operation-vocabulary.adoc[ADR-019]'s addendum, in its own vocabulary (*operation*, not
  `registerHelper`): `RawBars.renderWithOperations` (strict, core syntax) and
  `MaxBars.renderWithOperations` (lenient, infix/pipe surface), with `renderRawWith` / `renderMaxWith`
  JS facades. The kernel `rt.block` branch and the marshaller generalised exactly as anticipated here;
  the surface differences (RawBars has no hash/block-params; MaxBars has the full surface once its head
  grammar drops the top-level pipe rung, so `pass:[as |x|]` parses and a head pipe is parenthesised) are
  recorded there. Gated by the `op:raw-*` / `op:max-*` conformance cases.
* *Lab surfacing:* a user block helper in the Lab's `helpers.js` editor runs in the same Worker (ADR-018);
  no new capability, but the helpers pane copy should show a block example.

== Phase 3 addendum: the hash + block-param channel (design)

*Status:* Accepted — *implemented*. Resolves the deferred `options.hash` and block-param surface for user
block helpers, routing a block application's hash and `as |a b|` names to `options.hash` and body bindings
*without* (a) changing the meaning-free core AST, (b) rewriting the built-in block helpers, or (c) a
tagged-`Value` hack. A user block helper's full `options` surface is now `fn`/`inverse`/`hash` plus
`options.fn(ctx, { data, blockParams })`; only `ids`/`loc`/`lookupProperty` throw. Gated by
`block:hash`/`block:params`/`block:hash-params-data` (`test:compile`) and Lab unit tests.

=== The constraint, restated

The surface folds a block head's hash into a trailing `pass:[(dict …)]` argument and `as |a b|` into
trailing `pass:[Lit (VString "a")]` arguments (xref:surface.adoc[] §5.4–5.5), then the engine evaluates
the head's args to `Array Value` before the `Operation` runs. At that boundary the hash dict and the
name strings are indistinguishable from ordinary positional `Value`s. The built-ins cope because they
*know* the convention (`eachH` reads trailing string args as block-param names; `partialH` reads the
trailing dict as its hash). A *user* (Handlebars-style) helper does not — it expects `options.hash` and
body-bound block params.

=== Design: reserved markers + an explicit `Ctl` channel, built-ins unchanged

The key move keeps built-ins untouched: the surface emits the hash and each block-param name as *reserved
marker operations* that *evaluate to exactly the value the built-ins already expect*, while the engine
*additionally* extracts them — recognised structurally, from the head application's arg expressions — into
two new `Ctl` fields that only the user-helper marshaller reads.

. *Surface markers (FullBars desugar).* Collected hash pairs desugar to a trailing `pass:[(@hash k v …)]`
  instead of `pass:[(dict …)]`; each `as |name|` to `pass:[(@param "name")]` instead of a bare
  `pass:[Lit (VString "name")]`. The `@`-prefix makes them *unspellable by users* (surface `@x` strips the
  `@` to the scoped helper `x`), so they cannot collide with a real helper or data field — but they are
  *not* registered prelude operations (that would list them in the generated helper catalog, which has no
  hide mechanism — `dict`/`elif` already show there). They are recognised *structurally*, below.

. *Engine seam + `Ctl` channel.* The `Engine` record gains a small pluggable `blockArgs` splitter
  `Array Expr -> { positional :: Array Expr, hash :: Maybe Expr, params :: Array String }`; the kernel
  driver stays generic (it calls the seam, evaluates the returned `positional` for the `Operation`, and
  evaluates `hash` once to seed `Ctl`). FullBars supplies the marker-aware splitter; RawBars/MaxBars (no
  such markers) supply the identity split — so neither the catalog nor the meaning-free core changes. `Ctl`
  gains `hash :: Maybe Value` and `blockParams :: Array String`. *Built-ins keep working* because the
  splitter, by default, still appends the hash dict + name strings to `positional` exactly as today — the
  channel is *additive* (the new `Ctl` fields), and only the user-helper marshaller reads them and forwards
  a trimmed positional list.

. *The user-helper marshaller (interpreter).* For a block call it now: passes `options.hash = ctl.hash`
  (the dict); binds each `ctl.blockParams[i]` to the matching value the helper supplies via
  `options.fn(ctx, { blockParams: [v0, v1] })` (a sibling of the Phase-2 `data` frame — same pushed-frame
  mechanism); and *strips* the trailing marker values from the positional `args` it forwards to the JS
  function, so positional alignment matches Handlebars (`(items, options)`, not `(items, hashDict,
  "name", options)`).

. *The compiler.* The emitter already lowers native `each`/`with` with block-param names as a separate
  argument, so they are unaffected. For a *user* block (`rt.block`), the emitter — which sees the markers
  in the AST — emits the hash and block-param names through a new trailing options argument to `rt.block`;
  `rt.block` then builds `options.hash` and binds block params exactly as the interpreter does. The
  positional `args` it forwards exclude the markers. Gated by `test:compile`, so the two paths stay equal.

=== Why this is the right shape

* *No core-AST change.* `@hash`/`@param` are ordinary `App` nodes; the meaning-free `Block` is untouched.
* *No built-in rewrite.* The markers evaluate to the built-ins' existing inputs, so `each`/`with`/`partial`
  and every existing conformance case are unchanged.
* *No tagged `Value`.* The hash stays a plain `VObject`; the split is structural (marker expressions),
  resolved before the `Operation` boundary, not by inspecting a runtime value.
* *Symmetry with Phase 2.* Block-param binding reuses the `options.fn(ctx, { … })` second-argument frame
  (`{ data }` ⇒ scoped `@vars`; `{ blockParams }` ⇒ named bindings) — one mechanism, two key shapes.

=== Risks / review notes

* *Desugar-output churn.* Emitting `@hash`/`@param` changes the desugared AST (and therefore the compiled
  JS) for every hash / block-param template; AST-shape and highlight goldens, and `test:compile`, must be
  regenerated and stay green. This is mechanical but wide.
* *Catalog stays clean.* Because the markers are recognised by the `Engine` seam — not registered as
  prelude operations — they never reach `preludeSchema`, so the generated helper catalog (and
  `check:catalog`) is untouched. The `@`-prefix also keeps them unspellable by users, so a data field
  named `hash`/`param` can't collide.
* *Implementation order (landed, each step independently green).* (1) the `Engine.blockArgs` seam +
  `Ctl.hash`/`blockParams`, default identity, threaded by the driver (behaviour-preserving); (2) the shared
  `core` marker splitter + surface emit + compiler central demarker (behaviour-preserving — `test:compile`
  270/270); (3) the interpreter marshaller + compiler `rt.block` channel *consume* the channel
  (`options.hash`, block-param binding) + conformance cases (`test:compile` 273/273) + Lab tests; (4) docs.
  *All done.*
* *Two refinements found while implementing.*
  ** *The split utility lives in `core`.* Both the kernel driver (interpreter seam) and the `compile`
     emitter need it, and their only common dependency is `core`; it is a pure structural `Expr` transform
     (recognise reserved `@hash`/`@param` markers, demarker the positional), giving no *meaning*, so it sits
     in `core` without violating the meaning-free boundary. The default seam can then be the marker-aware
     split for *every* dialect — a no-op when no markers are present (RawBars/MaxBars/MinBars).
  ** *`@hash` marks **block** hash only; inline hash keeps `dict`.* The seam runs only on the *block* path
     (`applyBlock`); the inline application path (`evalExpr (App …)`) has no seam, so an `@hash` there would
     reach `resolve` and throw. So the surface emits `@hash` only when desugaring a *block* head's hash;
     `{{ f x k=v }}` (inline) still desugars to a trailing `dict` (ADR-018 inline hash, unchanged).
