= The core model
:navtitle: The core model

FlatBars rests on a few decisions. Every later rule is a consequence of them.

== 0. Two phases: a skeleton, then a walk

The core is a *parser*. Its entire output is a *skeleton AST* — a uniform tree of `Content`,
`Output`, and `Block` nodes (xref:evaluation.adoc[]). The parser attaches *no meaning*: it does not
know what any identifier does, does not know which identifiers are "helpers," does not know `else`,
and performs no checks beyond "is this well-formed structure."

Meaning is a *second pass*: a *walk* over the skeleton, supplied by the engine you build. The walk
validates the tree against the engine's rules and interprets it — precisely the relationship
between a JSON document and a JSON Schema. FlatBars defines the tree and the walking contract; the
engine defines the schema and the interpreter.

Everything below describes the interpretation of the reference engine, *FullBars*. A different engine may choose
differently; the core does not care.

== 1. Everything is a helper application

A template is a sequence of *content* and *outputs*. An output evaluates one expression and writes
its value. The only compound expression is a *helper application*.

[source,text]
----
{{{city}}}                          <1>
{{{lookup this "city"}}}            <2>
{{{upcase (lookup this "name")}}}   <3>
----
<1> Calls the helper `city` with no arguments. Not a variable, not `this.city`.
<2> Reads the `city` field of the current context, by calling the helpers `lookup` and `this`.
<3> `upcase` applied to one argument — the grouped sub-application `(lookup this "name")`.

There are *no variables*. The parser sees `city` as an identifier at the head of an application; the
engine resolves it in the *helper environment* and invokes it.

== 2. Application is juxtaposition; parentheses are grouping

`head arg1 arg2` applies. Parentheses do not mean "call"; they *group* a multi-token application so
it fits a single argument slot. A whole top-level expression therefore needs *no* parentheses:

[source,text]
----
{{{lookup this "age"}}}             top-level application — no parens
{{{upcase (lookup this "name")}}}   upcase of ONE argument (the group)
{{{upcase lookup this "name"}}}     WRONG: upcase applied to THREE arguments
----

This is the {hbs} subexpression model (and ML/Haskell-style application), *not* Lisp prefix
notation where every call is parenthesized. The only parentheses you ever write group a nested
application that sits in argument position.

== 3. The head of an application is always a name

The operator position holds an *identifier*, never a computed value. Nothing in the language
produces a callable value, so nothing else can sit there. This is enforced syntactically for blocks
(the closing `pass:[{{/name}}]` must repeat the name) and is what keeps a `Value` free of functions
(xref:evaluation.adoc[]). Higher-order use goes through a helper such as `apply`.

== 4. Scope is helpers, installed by blocks

Because a bare name is a helper call, *scoped state is just scoped helpers*. A block helper such as
`each` installs nullary helpers (`index`, `first`, the item context `this`, …) for the duration of
its body, then removes them.

[source,text]
----
{{#each people}}
  {{{lookup this "name"}}} is number {{{index}}}   <1>
{{/each}}
{{{index}}}                                         <2>
----
<1> Inside the block, `index` and `this` resolve — `each` installed them.
<2> Outside, `index` is undefined; resolving it is a validation error in the engine walk.

This replaces {hbs}' `@index`/`@parent`/context-stack with ordinary lexical scoping over the helper
environment. There is no `@` namespace and no `../` operator in the core.

== 5. No keywords — not even `else`

The core reserves *nothing*. `true`, `false`, `null` are not literals; they are reference-engine
helpers `(true)`, `(false)`, `(null)`. HTML escaping is the helper `escapeHtml`; the core never
escapes. And *`else` is not special*:

[IMPORTANT]
====
The *word* `else` never reaches the lexer or the parser. Branching is written with a *separator* —
the bare double-stash `pass:[{{ name args }}]` — which the core keeps as a meaningless marker:

[source,text]
----
{{#if cond}}
  yes
  {{else}}     <1>
  no
{{/if}}
----
<1> The lexer recognizes the double-stash *shape* and the parser emits `Sep "else" []` — a flat
marker sitting in `if`'s body. It assigns `else` no meaning. The reference `if` helper splits its
body at that separator (xref:evaluation.adoc[]). The name is the engine's choice — `else`, `el`,
`elif`, `otherwise`, `case`, `default`; the core never singles any of them out. A lone separator,
with no enclosing block to interpret it, simply renders as an application of its head.

The core *recognizes* the inverse opener `pass:[{{^x}}]` structurally — it records the opener sigil on
the `Block` node (`Section` vs `Inverse`) but assigns it no meaning. FullBars desugars `pass:[{{^x}}]`
to `pass:[{{#unless x}}]`; the austere RawBars and MaxBars dialects reject it (write the `unless`
helper). See xref:directives.adoc[].
====

== 6. No sugar in the core

If a construct can be explained as a rewrite to a smaller one, it does not belong in the core; it
belongs in the xref:surface.adoc[surface dialect]. `pass:[{{name}}]` (escaped), `a.b.c`, `@index`,
`../x`, `as \|x\|`, and `pass:[{{> p}}]` are *all* surface sugar.

== 7. One parser, four languages

Because the parser attaches no meaning, the *same* lexer and structural tree serve languages with
incompatible semantics — the dialect supplies the meaning through the `parseExpr` / `parseHead` seam
and the shape gates, never a fork of the grammar:

* *RawBars* — the meaning-free core itself, written out (`pass:[{{{ lookup this "x" }}}]`).
* *MinBars* — a Mustache-compatible *peer* engine, with its own context-stack scope and Mustache
  truthiness (`0` and `pass:[""]` are truthy); it passes the vendored `mustache/spec` suite.
* *FullBars* — the Handlebars-faithful reference engine (`pass:[{{ name }}]`, dotted paths,
  `pass:[{{#each}}]`).
* *MaxBars* — the full FlatBars surface language: FullBars plus infix operators and pipes.

That MinBars (Mustache) and FullBars (Handlebars) — two *mutually incompatible* template languages,
differing in scope rules and truthiness — both render through one structural core is the demonstration
that the parser is universal across the `pass:[{{ }}]` family. RawBars is that core exposed; MaxBars is
FlatBars's own maximal language on top. The normative contract for all four is this spec, not any one
dialect.

== 8. One compiler, too

The same generalization carries to compilation (xref:adr-0011-compile-to-js.adoc[ADR-011]): there is
*not* a per-dialect compiler. A single meaning-free *emit driver* (`FlatBars.Compile`) walks the lowered
core AST and calls into a pluggable `Emit` record — the fourth instance of the IoC pattern, alongside
interpret, desugar, and validate. The dialects on the kernel ladder do not have separate compilers; they
have separate *front-ends* that desugar to the same core, then share one driver and one `Emit`:

* *RawBars* parses core directly, then `compile meta emit nodes`.
* *FullBars* / *MaxBars* desugar the surface (the `parseExpr` seam, block params, MaxBars infix/pipes)
  to the same core AST, then call the *same* `compile` with the *same* emit rules — MaxBars `score >= 50`
  is already core `App` by the time the compiler sees it, so it compiles for free.

So "compiles to JS" is a property of the *core*, inherited by every surface that lowers to it — not a
RawBars-only feature. The `test:compile` gate asserts the compiled JS is byte-identical to the
interpreter for every golden case across these dialects, so the compiler can never silently diverge from
the walk.

MinBars is the one engine *not* on this driver: as a Mustache *peer* (its own context-stack scope and
truthiness, no kernel lowering) it compiles through a separate inlining model
(xref:adr-0016-minbars-compile.adoc[ADR-016]). That is a deliberate factoring — folding Mustache
semantics into the kernel `Emit` would add code and drift, not remove it — not a gap.

== A note on naming

The mark is a set of *bare rods*: the {hbs} braces stripped to their vertical strokes. The triple
stash `pass:[{{{ }}}]` — the core's one and only inline output form — is the logo's source.
