= ADR-0029: i18n via a host-plugged `t` (translate) operation, not bundled CLDR
:navtitle: ADR-029 i18n helper
:hbs: Handlebars

*Status:* Accepted — *implemented* 2026-06-05 (the blessed `t` prelude operation, interpreter +
compiled runtime; the FlatBars Lab demonstrates the seam via native `Intl` — see the amendments). *Date:*
2026-06-05. Builds on
xref:adr-0001-structural-parser-and-walker.adoc[ADR-001] (helpers are the meaning plug-in; the core stays
meaning-free), reuses the IoC callback shape of
xref:adr-0022-analyse-mode.adoc[ADR-022] (truthiness is a per-engine lambda the host plugs in, seeded into
both interpreter and compiled runtime, *no per-file config, no baked data*), extends the user-extension
path of xref:adr-0018-user-defined-helpers.adoc[ADR-018] (`registerHelper`), and is gated by the
compile ≡ interpret invariant of xref:adr-0011-compile-to-js.adoc[ADR-011]. It respects the dialect-purity
boundaries of xref:adr-0007-minbars.adoc[ADR-007] (MinBars is *Mustache*) and
xref:adr-0009-fullbars.adoc[ADR-009] (FullBars is *Handlebars-faithful*), using the engine-level opt-in
precedent of xref:adr-0015-set-delimiters.adoc[ADR-015] (set-delimiters is a MinBars-only knob, not a
global). Escaping follows xref:adr-0002-escaping-and-value-policy.adoc[ADR-002].

== Context

The https://en.wikipedia.org/wiki/Comparison_of_web_template_engines[Wikipedia comparison of web template
engines] scores FlatBars *i18n: No*. The evidence is direct: the 90-operation prelude
(`FullBars.preludeSchema`) ships no `t` / `translate` / `gettext`. Two facts frame the decision:

* *This is the company we keep.* {hbs} and Mustache *also* have no built-in i18n — their ecosystems do it
  with userland helpers/lambdas (i18next, `handlebars-i18n`, Mustache lambdas). So "absent from the core"
  is not anomalous; the gap is a *workflow/DX* gap, not a correctness gap.
* *i18n is meaning, and meaning is plugged in, not built in (ADR-001).* Real localization is not string
  substitution: it needs *pluralization* (CLDR gives Polish/Arabic/Russian 3–6 plural categories),
  *gender/select*, and locale-aware *number/date* formatting (ICU MessageFormat is the de-facto standard).
  A naive key-lookup `t` produces grammatically wrong output for most languages — *worse* than nothing,
  because it looks finished.

Three hard constraints fell out of team review (debate recorded against this ADR):

. *No CLDR/ICU data in our core or runtime.* The compiled runtime (`flatbars-runtime.mjs`) and the
  committed Lab bundle are size-gated; CLDR plural data is tens of KB and would tax *every* compiled
  template, including the majority that never localize.
. *The prelude is one shared schema across all four dialects.* Adding `t` to the base prelude adds it to
  *MinBars* (breaking the "pure Mustache" claim, ADR-007) and *FullBars* (Handlebars ships no `t`,
  ADR-009) — a faithfulness regression even though byte-identical conformance would stay green (the spec
  corpora never call `t`).
. *Whatever ships must satisfy compile ≡ interpret (ADR-011)* or `test:compile` goes red.

== Decision

Adopt the truthiness pattern (ADR-022) for localization: *FlatBars supplies the call site; the host
supplies the brain; we never bundle CLDR.*

. *`t` is a blessed operation in the shared kernel prelude* (`Kernel.Prelude`), reserved for the
  *core-surface family* — *RawBars, FullBars, and MaxBars* — and *absent from MinBars* (the separate
  Mustache peer engine has its own closed prelude, so adding to the kernel prelude never touches it; ADR-007
  stays intact). *RawBars is included precisely because it is the desugared core surface* (not a
  meaning-free substrate): FullBars's `pass:[{{t …}}]` desugars to a core `t` operation, so the operation
  *must* exist at the RawBars level for the desugar target to be complete, and RawBars runs the same
  prelude/engine. As implemented, the prelude `t` ships only the *fallback* (return the key unchanged); it
  carries no locale or CLDR data. Because — like every prelude operation — `t` only fires when applied with
  arguments (`pass:[{{t "k"}}]`), a bare `pass:[{{t}}]` still reads the data field `t`, so nothing is
  shadowed.

. *The host supplies the brain by registering `t`* (the IoC seam of ADR-018), not via a separate callback
  parameter: the interpreter's `renderWith` helper bag and the compiled runtime's `rt.register("t", fn)`
  both shadow the prelude fallback. The registered function receives the *message key* and the *named
  arguments* (the `key=value` hash as a trailing dict) and closes over the locale (e.g.
  `pass:[(key, args) => translate(locale, key, args)]`). The host owns the catalog, locale resolution, and
  all CLDR/ICU behaviour (plurals, select, gender, number/date) — typically its existing i18n library, or
  the browser's native `Intl` (see the 2026-06-05 amendment). *FlatBars ships no plural rules and no CLDR
  data.* Conceptually this is the truthiness pattern (ADR-022) — a host-plugged rule, the same on both
  interpreter and compiled paths — reusing the registration seam rather than a bespoke env field.

. *Surface.* The head is `t`, the first argument is the message key, the rest are named arguments:
+
[source,handlebars]
----
{{t "cart.summary" count=cart.size name=user.name}}
----
+
In MaxBars this also composes with pipes (`cart.size | t "cart.summary"` is *not* the shape; the key is
the head argument — pipe sugar applies to value-producing operations, see xref:maxbars.adoc[]).
+
*Name: lowercase `t`, not `T`.* An uppercase `T` was considered for ergonomics — it reads more like a
sigil and is harder to overlook in a dense template — and rejected. `t` is the universal i18n function
name (i18next, gettext, Rails, Vue, react-i18next), so it is recognized on sight and lets ported templates
work unchanged; the prelude is case-sensitive, so `T` would silently break `pass:[{{t …}}]`. It would also
be the *only* uppercase operation among the 90 lowercase ones. Most importantly, `t` is an *operation
name*, not a sigil (FlatBars has no keywords — "the head of an application is always a name", ADR-001);
making it look like grammar would miscategorize it. The "don't overlook it" need is met in the *editor*
layer instead — bold tag emphasis (ADR-026) and operation-name painting both already make `pass:[{{t …}}]`
stand out — which is the correct place for visual salience. No `translate` alias ships (canonical-only;
legacy spellings are a lint concern, ADR-019).

. *Escaping is unchanged (ADR-002).* The callback returns a `String`; it lands *escaped* in
  `pass:[{{t …}}]` and *raw* in `pass:[{{{t …}}}]`, exactly like every other helper, with `safe` as the
  SafeString escape hatch. Messages that intentionally carry markup use the triple-stache. *No new
  escaping axis is introduced.*

. *Missing-key policy: fallback-and-flag, never throw.* With no `t` registered the prelude fallback renders
  the key unchanged (a host that returns a marker for a missing key gets that instead), and *analyse mode*
  (ADR-022 Part B) / the linter can flag it. A strict mode that errors on a missing key is opt-in (for CI,
  not render). Production renders never hard-fail on one missing translation.

. *compile ≡ interpret.* The prelude fallback is *pure* (return the key), so a template using `t` with no
  host registration renders byte-identically interpreted and compiled. With a host `t`, the same registered
  function runs on both paths (`renderWith` for the interpreter, `rt.register` for the compiled runtime).
  `test:compile` gates the no-host case; the with-host parity is verified directly.

== Consequences

* The Wikipedia *i18n: No* becomes *Yes (host-plugged)* for RawBars/FullBars/MaxBars, with the honest
  footnote that the plural/format brain is the host's — which is exactly how i18next-backed {hbs} works.
* The catalog gains a `t` entry (`FullBars.Catalog`, the LSP `operations.json`); `npm run gen:catalog` and
  `npm run gen:operations` regenerate them and `check:catalog` / `check:operations` gate the drift. `t` is
  now hover-documented and operation-painted in the editors.
* *Only MinBars is unaffected* — its separate closed prelude does not gain `t`, so ADR-007 purity and the
  Mustache conformance claim are untouched. RawBars *does* gain `t` (ADR-008's `nonEmpty` truthiness is
  orthogonal and unchanged); this is required, not incidental — it is the desugar target FullBars/MaxBars
  lower to. FullBars's `t` is an *extension* beyond Handlebars (faithful to the workflow, not a Handlebars
  built-in); `hbs-conformance` is unaffected because the corpus never calls `t`.
* Zero bundle-size impact and no behavioural change for templates that don't localize: no CLDR ships, and a
  bare `pass:[{{t}}]` still resolves to the data field.

=== What we explicitly do NOT do

* *No ICU MessageFormat engine in-core, no CLDR plural rules in our runtime* (rejected option D in the
  debate): heavy data, violates meaning-free + the bundle gates. Plurals are the host's job.
* *No per-file `@locale` directive.* Locale is the host's, closed over by the registered `t` — mirroring
  ADR-022's rejection of per-file `@truthiness`.
* *No `t` in MinBars.* It lives in the *kernel* prelude (shared by RawBars/FullBars/MaxBars), never in
  MinBars's separate Mustache prelude — so the Mustache-purity claim stays clean without a conditional
  mechanism (rejected option B was forcing it onto *every* engine, which would have hit MinBars).
* *No dedicated translate-callback parameter or new env field.* The host plugs in through the existing
  ADR-018 registration seam (`renderWith` / `rt.register`), which already marshals a host function and
  shadows the prelude fallback — no second mechanism.

== Alternatives considered (debate ratings)

[cols="1,4,1"]
|===
| Option | Summary | Verdict

| A — recipe only
| Document `registerHelper('t', …)` + i18next; ship no engine surface. The honest "you can already do
  this today" answer, and how {hbs}/Mustache users localize.
| *Adopt as the interim*, but it documents a workaround rather than closing the gap.

| B — `t` in the base prelude
| Simplest, but adds `t` to MinBars + FullBars schemas.
| Rejected — pollutes Mustache/Handlebars faithfulness.

| C — opt-in module + host `translate` callback
| This ADR. Truthiness pattern applied to localization; no CLDR shipped; dialect-gated.
| *Accepted (proposed).*

| D — full ICU/CLDR in-core
| Correct plurals out of the box, but tens of KB of data in core/runtime.
| Rejected — violates meaning-free + bundle gates.

| E — `number` / `date` / `selectPlural` (+ `relative`) helpers
| A locale-aware formatting helper set, same host-register discipline.
| *Adopted* — all are blessed prelude operations alongside `t` (pure fallbacks: plain text; the English
  one/other rule; "N units ago"). All four accept an Intl options hash — the trailing dict passes through
  with no arity change (the fallbacks ignore it; the host reads it).
|===

== Follow-ups

. ✅ *Done — the interim recipe and Lab demo:* the `/localize` guide renders `pass:[{{t …}}]` live via the
  host-register seam, on the browser's native `Intl` (see the 2026-06-05 amendment), gated by `check:i18n`.
. ✅ *Done — this ADR (C):* the `t` prelude operation (RawBars/FullBars/MaxBars; not MinBars), the host
  brain via the ADR-018 registration seam (interpreter + compiled runtime), the pure key-returning
  fallback, catalog/operations generation, and `test:compile` parity.
. ✅ *Done — the E formatting set:* `number` / `date` / `selectPlural` / `relative` are blessed prelude
  operations alongside `t` (pure fallbacks — plain text, the English one/other rule, and "N units ago" —
  overridden by the host's native `Intl`). All four read an Intl options hash
  (`pass:[{{number n style="currency" currency="EUR"}}]`, `pass:[{{selectPlural n type="ordinal"}}]`,
  `pass:[{{relative v u numeric="always"}}]`), which the trailing dict delivers without an arity change.
. *Conformance note:* add an `i18n` row to xref:fullbars-compat.adoc[] documenting that the `t` operation
  (shared by RawBars/FullBars/MaxBars) is an *extension* beyond Handlebars (faithful to the workflow, not a
  Handlebars built-in), the same framing ADR-018 used for `registerHelper`.

== Amendment (2026-06-05): the Lab demonstrates the seam via native `Intl` — i18next is not vendored

The question arose of whether to vendor *i18next* into the FlatBars Lab and build an i18n guide around
it, the way the Lab vendors `jsonata` (`lab/vendor/jsonata.mjs`, ~78 KB) for the data-shaping guide. Team
review (debate recorded against this ADR) rejected vendoring and adopted *option C+*: the Lab demonstrates
the i18n integration *seam* using the browser's native `Intl`, with i18next available only as an
*unbundled* documented escape hatch.

Decision and rationale:

. *No i18next in the bundle.* The browser already ships the CLDR brain — `Intl.PluralRules` (every
  language's plural categories), `Intl.NumberFormat`, `Intl.DateTimeFormat` — at *zero* bytes. JSONata
  earned its vendor because data-shaping-before-render has no platform equivalent; i18n's plural/format
  machinery *is* the platform, so vendoring i18next would be redundant weight plus a version/CVE pin and an
  ecosystem blessing. The Lab vendors a library only when the platform can't already do the job.

. *Demonstrate the seam, framed as Lab-as-host.* A live card (`tutorials/src/components/TryI18n.jsx`,
  sibling of `TryJsonata.jsx`) and a `/localize` guide wire a `t` helper to native `Intl` via the existing
  `registerHelper` / `renderWith` path (ADR-018) — *not* a new engine feature. This *reinforces* the
  ADR's "i18n is the host's job" thesis (the Lab is acting as the host) rather than implying FlatBars does
  i18n; the page says so explicitly.

. *No dependency on the unimplemented `t` operation.* Riding the ADR-018 `registerHelper`/`renderWith`
  seam, the demo ships today as the living proof of follow-up 1 (the interim recipe) and migrates to the
  blessed `t` (follow-up 2) when the module lands.

. *Cheap gate.* `scripts/check-i18n.mjs` (mirroring `check:jsonata`) renders the `pass:[{{t …}}]` cells
  across locales — including one with non-trivial plurals (Polish: one/few/many/other) and per-locale
  number grouping — and asserts the output. There is no vendored dependency to pin.

. *Escape hatch, unbundled.* The guide shows a one-paragraph stub for swapping the `Intl` wrapper for
  i18next or ICU MessageFormat (`@formatjs`) in a real host — fidelity without the bytes.

Future option (non-blocking): if users ask to demo *their* i18next setup, load it lazily via dynamic
`import()` on demand, never in the base bundle, keeping the 0-byte default.

=== Lab integration (2026-06-05): first-class catalog.yaml + config.yaml views

The Lab exposes the seam as two dedicated sidebar *views* (not partial tabs), mirroring the engine's
data/config split: a *LOCALIZATION* section with *`catalog.yaml`* (the message DATA, locale-keyed; shown
on every surface except MinBars) and a generalized *`config.yaml`* (the former Stem-only `stem.config.yaml`)
that now also carries `i18n.locale` on the t-surfaces and `minbars.truthiness` on MinBars — the latter
replacing the old mustache.js-truthiness UI toggle. The render routes RawBars/FullBars/MaxBars through the
helper Worker (`lab/i18n.mjs` `buildI18nHelpers`), so
`pass:[{{t …}}]`/`number`/`date`/`selectPlural`/`relative` resolve from `catalog.yaml` bound to the locale
the Lab parses from `config.yaml` (its inline `parseConfigYaml`). One shared catalog/config (the groups are
surface-scoped), not per-surface storage.
The `/localize` *Open in Lab* round-trips the catalog + locale into those views (`cat`/`loc` workspace
fields). The data pane is shared by data/config/catalog, so a `dataPaneMode` flag routes edits by what the
pane displays — config/catalog keystrokes never fall through to `data.yaml`.

==== The Lab's MinBars truthiness default is `mustacheJs`, by design

The engine, CLI, and JS facade default MinBars to the *language-agnostic spec* rule (`0`/`""`/`{}` truthy,
as in Ruby/Python Mustache); `mustacheJs` (`0`/`""` falsy) is the opt-in (`renderMinbars({compat})`,
`flatbars --mustache-js`). The *Lab* deliberately inverts that default: `config.yaml`'s
`minbars.truthiness` starts at *`mustacheJs`*, not `spec`.

The reason is the Lab's audience and habitat. It runs in the browser, where `mustache.js` is *the* Mustache
people have used — so its truthiness (`0`/`""` falsy) is what a JS author already expects. Defaulting the
playground to the rule its visitors carry in their heads minimises surprising "why did my `0` render?"
moments, especially for beginners meeting Mustache through the Lab. The spec rule stays one keystroke away
(`minbars.truthiness: spec`); the engine's own default is unchanged, so nothing downstream of the Lab
shifts. This is a *presentation* choice scoped to the playground, not an engine policy change (ADR-022).

Consistent with that default, the share link omits the truthiness field for `mustacheJs` and records only
the spec opt-out (`mj=0`), keeping the common link compact. (One consequence: a pre-2026-06-05 MinBars link
that relied on the *old* default-`spec` — no `mj` field — now renders under `mustacheJs`; such links predate
the i18n/config work and are vanishingly rare. Add `minbars.truthiness: spec` to restore the old reading.)
