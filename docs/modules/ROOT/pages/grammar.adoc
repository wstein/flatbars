= 2. Syntactic grammar
:navtitle: 2. Syntactic grammar

This is the *complete* core grammar. It produces a *skeleton AST* — structure with no meaning. There
is one output form, one application shape, and one block form. Everything a {hbs} user expects
beyond that is built in the xref:surface.adoc[surface dialect] or supplied by the
xref:prelude.adoc[engine walk].

== 2.1 Grammar (normative)

[source,text]
----
Template  ::= Node*

Node      ::= Content                                   (* literal text *)
            | Output
            | Block
            | RawBlock
            (* Comments are removed by the lexer and never appear here. *)

Output    ::= "{{{" Expr "}}}"

Block     ::= "{{#"   Ident Arg* "}}"
                  Template
              "{{/" Ident "}}"

RawBlock  ::= "{{{{#" Ident Arg* "}}}}"
                  RawText
              "{{{{/" Ident "}}}}"

Expr      ::= Literal
            | Ident Arg*            (* application; zero args = nullary call *)
            | "(" Expr ")"          (* grouping; a no-op around a whole expression *)

Arg       ::= Literal
            | Ident                 (* a bare ident in argument position is a nullary call *)
            | "(" Expr ")"          (* group a nested application into one argument *)

Literal   ::= String | Number

Ident, String, Number, RawText    (* from the lexer; see Chapter 1 *)
----

There is *no inverse clause* in `Block`: a block captures exactly one `Template`. There is no
`pass:[{{else}}]` and no `pass:[{{^}}]`. Branching is represented as ordinary nested `Block` nodes
that the engine walk interprets (xref:concepts.adoc[] §5).

== 2.2 Reading the grammar

One structure runs through all of it: *an application is an operator followed by arguments*, with the
operator *immediately after an opening bracket*. There are three brackets:

[cols="1,2,2",options="header"]
|===
|Bracket |Opens with |Yields

|grouping |`(` … `)` |a value
|output |`pass:[{{{]` … `pass:[}}}]` |writes a value (takes exactly one `Expr`)
|block |`pass:[{{#]` … `pass:[{{/n}}]` |writes a value, *and* captures its body as a sub-tree
|===

Because the output bracket takes *exactly one* `Expr`, and `Expr ::= Ident Arg*` is itself a whole
application, you write top-level applications *without* parentheses:

[source,text]
----
{{{lookup this "age"}}}     ok: one Expr, operator lookup with two args
{{{f a b}}}                 ok: operator f, args a and b
{{{(lookup this "age")}}}   redundant: the outer group wraps the whole Expr — a no-op
----

Parentheses are needed only to nest one application *inside another* as an argument, as in
`pass:[{{{upcase (lookup this "name")}}}]`. The head of an application is always an `Ident`; a group
never appears in head position.

== 2.3 Block heads must be identifiers

The block opener is `pass:[{{# Ident Arg* }}]` — the operator is a bare `Ident`, with the same
argument rules as an inline application — and `pass:[{{/Ident}}]` must repeat that identifier so the
parser can match nesting. *Computed block helpers are not expressible*: there is no
`pass:[{{#(pick) …}}]`. This is the one place the "head is always a name" rule is enforced
syntactically, and it is what makes `pass:[{{/each}}]` unambiguous.

== 2.4 Branching is nesting, not a clause

A block helper that wants alternatives reads them from *its own body* as nested blocks. The parser
treats them like any other child:

[source,text]
----
{{#if cond}}A{{#else}}B{{/else}}{{/if}}

parses to:

Block "if" [App "cond" []]
  [ Content "A"
  , Block "else" [] [ Content "B" ] ]
----

The parser assigns `else` no special status; the engine's `if` helper decides what a child named
`else` means (xref:evaluation.adoc[], xref:prelude.adoc[]).

== 2.5 What is *not* in the grammar

To make "no sugar in core" auditable, here is what a {hbs} author will look for and not find — each
has a home in the surface dialect or the engine:

[cols="1,2",options="header"]
|===
|Absent from the core |Where it lives

|`pass:[{{ }}]` (escaped output) |surface → `pass:[{{{ esc_html … }}}]`
|`pass:[{{else}}]`, `pass:[{{^}}]` |engine → nested clause blocks / the `unless` helper
|dotted/parent paths `a.b`, `../a`, `this.a` |surface → `lookup` / `parent`
|index & segment-literal paths `a.1`, `a.[k v]` |surface → `lookup` with number / string segments
|`@index`, `@key`, `@root`, … |surface → scoped engine helpers `index`, `key`, `root`, …
|hash arguments `key=val` |surface → trailing `(dict "key" val)` argument
|block params `as \|x i\|` |surface → binding-name arguments to the block helper
|`true` / `false` / `null` / `undefined` |engine helpers `(true)` `(false)` `(null)`
|partials `pass:[{{> p}}]`, `pass:[{{#> p}}]`, `pass:[{{#*inline}}]` |surface → `partial` / `inline` helpers
|decorators `pass:[{{* …}}]`, `pass:[{{#* …}}]` |engine block helpers
|===

== 2.6 Worked parse

[source,text]
----
template:  <li>{{{esc_html (lookup this "name")}}} — {{{index}}}</li>

Node[0] = Content "<li>"
Node[1] = Output (App "esc_html"
                       [ App "lookup" [ App "this" [], Str "name" ] ])   <1>
Node[2] = Content " — "
Node[3] = Output (App "index" [])
Node[4] = Content "</li>"
----
<1> The group `(lookup this "name")` is parsed away — grouping affects parsing only and leaves no
node. The abstract syntax is specified in xref:evaluation.adoc[].
