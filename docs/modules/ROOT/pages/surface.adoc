= 5. The surface dialect (sugar)
:navtitle: 5. The surface dialect

The core is austere by design. *BareBars Surface* is an optional dialect that recovers {hbs}
ergonomics by *compiling to the core skeleton*. It is a separate front-end — you can render core
templates without it, swap it, or write your own — but the reference Surface is specified here
because the xref:appendix-handlebars.adoc[Handlebars mapping] is defined in terms of it.

Surface adds nothing the core cannot already express. Every rule below is a *pure syntactic rewrite*
to the core. Where a rewrite names a helper (`esc_html`, `lookup`, `dict`, `partial`, …), that
helper must exist in the xref:prelude.adoc[engine].

[IMPORTANT]
====
*Parenthesis convention.* A top-level expression inside `pass:[{{{ }}}]` needs no grouping — it is
already one `Expr`. Parentheses appear only around a *nested* application in argument position. So
the desugaring of `pass:[{{ name }}]` is `pass:[{{{ esc_html (lookup this "name") }}}]` — `esc_html`
is the top-level operator (no wrapper), and `(lookup this "name")` is parenthesized because it is an
argument.
====

== 5.1 Output: `pass:[{{ }}]`, `pass:[{{{ }}}]`, `pass:[{{& }}]`

[cols="2,3",options="header"]
|===
|Surface |Core

|`pass:[{{ E }}]` |`pass:[{{{ esc_html E' }}}]`
|`pass:[{{{ E }}}]` |`pass:[{{{ E' }}}]`
|`pass:[{{& E }}]` |`pass:[{{{ E' }}}]`
|===

`E'` is `E` after the *path rewrite* (5.2). If `E'` is itself a multi-token application it is wrapped
in parentheses before being handed to `esc_html` (it is now an argument): `pass:[{{ upcase x }}]` →
`pass:[{{{ esc_html (upcase (lookup this "x")) }}}]`.

== 5.2 Paths become `lookup`

[cols="2,3",options="header"]
|===
|Surface path |Core

|`name` |`(lookup this "name")`
|`a.b.c` |`(lookup this "a" "b" "c")`
|`a.1` or `a.[1]` |`(lookup this "a" 1)`
|`a.[home town]` |`(lookup this "a" "home town")`
|`a/b` (legacy slash) |`(lookup this "a" "b")`
|`this` or `.` |`this`
|`this.a` or `./a` |`(lookup this "a")`
|`../a` |`(lookup (parent) "a")`
|`../../a` |`(lookup (parent (parent)) "a")`
|`@x` |`(x)`  (a scoped data helper — 5.5)
|`@../x` |`(x (parent))`
|===

(The right-hand forms are shown parenthesized because in Surface a path almost always lands in
*argument* position — e.g. as the argument of `esc_html`. When a path is the whole top-level
expression, e.g. `pass:[{{{ name }}}]`, the desugaring is the unwrapped `pass:[{{{ lookup this "name" }}}]`.)

`lookup` is *variadic*: it walks segments left to right, indexing objects by string key and arrays by
number, returning `VNull` at the first miss. `parent` is a scoped helper that block helpers install
to expose the enclosing context (5.5); it replaces {hbs}' implicit context stack with an explicit,
named one.

[NOTE]
====
A bare path `name` resolves to a *data field* (`lookup this "name"`), never to a helper, because
Surface always wraps it. This is the opposite of the core, where `pass:[{{{name}}}]` *calls* the
helper `name`. The two layers read the same text differently on purpose: Surface is for authors who
think in data; the core is for the desugarer and the engine.
====

== 5.3 Helper calls, literals, and subexpressions

Anything that is not a bare path is a helper call, exactly as in the core, with two literal
conveniences:

[cols="2,3",options="header"]
|===
|Surface |Core

|`true` / `false` / `null` |`(true)` / `(false)` / `(null)`
|`(helper a b)` |unchanged — grouping is already core
|`helper a b` (tag head) |unchanged — application is already core
|===

In *head* position a bare identifier is a helper; in *argument* position a bare identifier that is
not a registered literal is a path. So `pass:[{{upcase name}}]` →
`pass:[{{{ esc_html (upcase (lookup this "name")) }}}]`.

== 5.4 Hash arguments become a trailing `dict`

[cols="2,3",options="header"]
|===
|Surface |Core

|`pass:[{{helper a k1=v1 k2=v2}}]` |`pass:[{{{ esc_html (helper a (dict "k1" v1 "k2" v2)) }}}]`
|`pass:[{{#helper a k=v}}…{{/helper}}]` |`pass:[{{#helper a (dict "k" v)}}…{{/helper}}]`
|===

All `key=value` pairs collapse into a single `dict` value appended *after* the positional arguments —
the equivalent of {hbs}' `options.hash`.

== 5.5 `@data` and block params become scoped helpers

`each` and `with` install scoped helpers for the duration of their body; Surface `@`-variables are
calls to them, and block params rename them:

[cols="2,3",options="header"]
|===
|Surface |Core / mechanism

|`@index` `@key` `@first` `@last` |`(index)` `(key)` `(first)` `(last)` — installed by `each`
|`@root` |`(root)` — installed by the host at the top frame
|`{{#each xs as \|item i\|}}` |`{{#each xs "item" "i"}}` — `each` also installs `item` and `i`
|`{{#with o as \|x\|}}` |`{{#with o "x"}}` — `with` installs `x` alongside the shifted `this`
|===

Renaming via `as |…|` becomes positional *binding-name* arguments to the block helper.

== 5.6 Branches become nested clause blocks

Surface has no `pass:[{{else}}]` either: it rewrites the familiar separator into the nested clause
block the engine reads (xref:concepts.adoc[] §5).

[cols="2,3",options="header"]
|===
|Surface |Core

|`pass:[{{#if c}}A{{else}}B{{/if}}]` |`pass:[{{#if c}}A{{#else}}B{{/else}}{{/if}}]`
|`pass:[{{#each xs}}A{{else}}B{{/each}}]` |`pass:[{{#each xs}}A{{#else}}B{{/else}}{{/each}}]`
|`pass:[{{#if a}}A{{else if b}}B{{else}}C{{/if}}]` |`pass:[{{#if a}}A{{#else}}{{#if b}}B{{#else}}C{{/else}}{{/if}}{{/else}}{{/if}}]`
|===

`else` and `unless` are *engine* names. A different engine could read a clause named `otherwise` or
provide `elif`/`case`/`default`; Surface simply targets whatever the engine defines.

There is *no inverted-block sugar*. BareBars adopts Mustache's `pass:[{{^x}}]` in *no form* — for
"render when falsy" you write the `unless` helper explicitly: `pass:[{{#unless c}}A{{/unless}}]`.

== 5.7 Partials become `partial` / `inline`

[cols="2,3",options="header"]
|===
|Surface |Core

|`pass:[{{> name}}]` |`pass:[{{{ partial "name" this }}}]`
|`pass:[{{> name ctx}}]` |`pass:[{{{ partial "name" ctx' }}}]`
|`pass:[{{> name k=v}}]` |`pass:[{{{ partial "name" this (dict "k" v) }}}]`
|`pass:[{{> name ctx k=v}}]` |`pass:[{{{ partial "name" ctx' (dict "k" v) }}}]`
|`pass:[{{> (expr)}}]` (dynamic) |`pass:[{{{ partial (expr) this }}}]`
|`pass:[{{#> name k=v}}body{{/name}}]` |`pass:[{{#partial> "name" (dict "k" v)}}body{{/partial>}}]`
|`pass:[{{> @partial-block}}]` |`pass:[{{{ partial-block }}}]`
|`pass:[{{#*inline "name"}}body{{/inline}}]` |`pass:[{{#inline "name"}}body{{/inline}}]`
|===

Partials render *unescaped* — a partial produces markup, not a data value, so the desugaring is the
plain triple-stash with no `esc_html`. The partial *name* desugars to a `STRING` literal; a dynamic
partial keeps the computed expression. `partial`, `partial>`, `inline`, and the scoped
`partial-block` are engine helpers; see xref:appendix-handlebars.adoc#partials[A.6].

== 5.8 What Surface does *not* change

Comments, raw blocks, whitespace `~`, and brace-escaping are *core* features and pass through
untouched.
